**Changed: simplified UX** (after the first review round). The owner's principle: _your library lives on this iPhone; an account backs it up and keeps it in sync; signing out only pauses that._ No prompts beyond one sign-out confirmation, everything else is automatic. What differs from §1.5 below, which stays as the record of the data model (unchanged: no data loss, committed records never reassigned, uploads bound to the account that started them, nothing destructive on expiry):

- **Sign-in, no prompt** (replaces (f)/(g)'s dialog): `openLibraryForSignIn` (`library/sessionLibrary.ts`) opens the account's library (parked or new) and then runs the same crash-safe merge (`mergeRun.ts`, stages 1–3 unchanged) of this device's library into it at once, inside the sign-in's paused section; the merged records push with the next sync, the device library goes when nothing is left in it. A photo in another account's storage still stays behind (the device library is kept, unlisted, for it, with its `mergedInto` marker, so it never joins another account); a failed merge doesn't fail the sign-in. The same code path runs at every boot (`mergeDeviceLibrary`, after `resumeMerges`, in one paused section): a merge that failed or was interrupted is simply run again, `planMerge` being idempotent, so `completeMerge` is gone. The merge runs before the first pull, so a camera-roll photo the account already holds is matched (by `mediaLibraryAssetId`) only when the account library on this phone had pulled it already; a fresh account library gets the device's copy and the pull then adds the server's. `MergeOffer` and "Keep Separate" are gone.
- **Sign-out keeps the library open** (replaces (b) and (h)): `dropTokensAsync` (`utils/cloud-api/sessionStore.js`, also what a rejected session goes through) drops the tokens and nothing else; the session keeps its owner, so the same library is open now and at the next boot (`libraryForSession` opens an owner's library with or without tokens, the state `rebuildRegistry` already wrote for a signed-out migrated owner). Sync and backup stop (`withSyncPaused`), the revoke stays best effort. What is added while signed out belongs to that library and uploads when its owner signs in again. The device library is never returned to; it exists only before the first sign-in.
- **One confirmation, only when needed**: `confirmSignOutAsync` (`features/cloud/confirmSignOutAsync.js`) signs out at once when the open library has nothing pending (`pendingCount` from `useSyncStatus`) and no photo waiting for its upload or failed (`useBackupCounts`), else one Alert: "You have media that isn't backed up yet" / "It will upload the next time you sign in." / Cancel · Sign Out. The sign-out sheet (Keep / Remove) is gone; nothing in the UI removes a library.
- **Another account signs in** while A's library is open and signed out ((c) unchanged): B's library opens, A's stays parked with its pending changes and reopens, syncing again, when A signs in. No message.
- **Session expiry** ((a) without the Alert): a rejected refresh sets `tokens: null` and the app shows only the Settings row "Backup paused · Sign in to continue" above the pre-filled sign-in form, and the badge on the header avatar (`FloatingHeader`, the one place the avatar shows). An explicit sign-out lands in the same state, on purpose: both mean "this library's backup is paused".
- **Settings**: Account (signed in: the email and Sign out; else the reauth row when the session's owner is the open library's, the sign-in form, and, with no account library on the phone, the hint "Squidbox works without an account. Sign in to back up your photos and keep them in sync."), Backup & Sync whenever the open library is an account's, signed in or not. "Libraries on this iPhone" and its Remove are gone, with `readParkedCounts`, `atRiskCount`, the `closed` snapshot of the registry and `unsyncedCountsText`; `removeLibrary` stays for the merge's last stage. Parked libraries of other accounts stay on the phone with no way to free their space (`todo.md`).

Goal, decided by the owner: the app keeps one SQLite database and one set of file folders per **library**, and a library belongs to an **owner**: "This iPhone" (local-only) or account `U` on server `S`. One library is open at a time. Sync runs only for an account library with a valid session. Nothing is wiped as a side effect of signing in or out; removing a library is an explicit, counted action. The model makes a local-only mode (Apple HIG "Managing accounts", App Review 5.1.1(v)) possible; §5 says what of it is in scope now. Criteria as before: SIMPLE, ROBUST, CLEAN, DRY, fixed at the root.

## 0. Diagnosis (what the code does today)

- **One store.** `sync/db/client.ts` opens `squidbox.db` once (`openDatabase`, module singletons `db`/`opening`, never closed); `DatabaseGate` in `App.js` opens it and `MigrationGate` runs `useMigrations(getDb(), migrations)`. 21 files call `getDb()` (33 call sites): the providers (`AssetsProvider`, `AlbumsProvider`, `PostsProvider`), `useLiveQuery` → `watchQuery(getDb(), …)`, `useSyncStatus`, `useInspector`, `useRecordCounts`, `useSeedOrClose`, `AssetScreen`, `CreatePostScreen`, `Album.jsx`, `DeletedAssetsAlbum`, `SortableAssetGrid`, `useAssetSelectionActions`, `AssetPickerProvider`, `RandomSuggestionsModal`, `AiChatModal`, `useResortAlbumsByName`, `CloudSyncProvider`, and `worker.ts` (dynamic import). All of them resolve the database at call time, nothing caches a reference across calls; only a live watch holds one for its lifetime (stopped on unmount) and a sync run for its duration (single-flight). That is what makes a switch mechanical. `CloudProvider` sits _above_ `DatabaseGate` (`App.js`), so today's session logic can't read anything the gate owns.
- **One file set.** `utils/assets/files/constants.js` (`${documentDirectory}assetfiles/`) and `utils/assets/thumbnails/constants.js` (`…assetthumbnails/`), read by `getAssetFileUri`, `assetFileExistsAsync`, `deleteAssetFileAsync`, `createAssetFileDirectory`, `getAssetThumbnailUri`, `hasThumbnailAsync`, `createAssetThumbnailDirectory`, `deleteAssetThumbnailAsync`; consumers are `buildAssetAsync` (moves the picked file into the folder _before_ the record is saved), `createAssetThumbnail`, `uploadAssetFileAsync`, `uploadAssetThumbnailAsync`, `preloadAssetThumbnailsAsync` (resolves the folder per file, after a network call), `useSaveAssetsToMediaLibrary`, `AssetImage`, `CloudSyncProvider` (deletes the file after its upload). On web the `.web.js` variants keep presigned URLs in the global `webThumbnailUrls` map (`documentDirectory` is null on web). The downloads cache (`cacheDirectory/downloads`, `downloadAssetFileAsync`) is transient and stays global. iOS legacy `moveAsync` removes an existing destination first, then moves (`ios/Legacy/FileSystemLegacyModule.swift`), so a repeated move deletes what the first one moved; `getInfoAsync` on a directory always recurses.
- **Signing in as another user wipes everything.** `CloudProvider.startSessionAsync` runs `resetSyncForUser(db, user.id)` inside `withSyncPaused`; a different `lastSyncUserId` (`sync_meta`) runs `resetLocalSync`, which deletes every collection table, the outbox, the cursor and the first-sync flag, unsynced work included, after `confirmLoginAsync`'s generic warning. `lastSyncUserId === null` records the new user without a wipe, so an unknown owner's data is adopted silently. Files are never touched: A's `assetfiles/` stay on disk under B (the orphaned-files issue). `confirmLogoutAsync` says "All data on this device is removed" while `endSessionAsync` only clears the stored user (the comment in `CloudProvider` says the library is kept on purpose).
- **Sync can't be interrupted or re-bound.** `withSyncPaused` waits for the whole running sync (`singleFlight.exclusive`), and `pullPhase` loops until `hasMore` is false, so a sign-out during a first sync would wait minutes. `singleFlight`'s trailing re-run (`rerun`) doesn't consult `syncActive`, and `withSyncRun` resolves `getDb()` and the HTTP transport at run time, so a run queued before a sign-out executes afterwards on whatever database and session are current.
- **Sessions aren't bound to a server.** `apiTokenStore(.web).js` keeps two keys (`accessToken`, `refreshToken`) with no server or user; `API_BASE_URL` (`apiBaseUrl.js`) is the env URL or, under `dev:local`, the dev server's origin (`window.location.origin` on web, the tunnel host on a phone, which changes per run). `loginAsync` and `refreshAccessTokenAsync` write the access token, then the refresh token (a crash between the two leaves a token pair the server will reject at the next refresh). `logoutAsync` posts through `apiWithAuthentication`, which attaches a bearer the route doesn't check: `/auth/logout` has no `preHandler`, so the "refresh rotates the token, then logout revokes the stale one" failure the brief describes cannot happen on today's code (the route never answers 401). It would the day the route gets one, and the bearer is noise, so the plan still moves it to plain `api`. `initializeCloudAsync.handleMissingUser` clears the tokens on any error, a network error included. A rejected refresh ends the session (`notifySessionExpired` → `endSessionAsync` + "Signed out" alert).
- **A backup run outlives a session change.** `CloudSyncProvider.syncAssets` loops over `readUnsyncedIds`; each `uploadFileAsync` reads whatever access token is stored at that moment and refreshes whatever refresh token is stored on a 401. After a switch it uploads A's file with B's token into B's storage, marks A's record and deletes A's local copy; any failure writes `syncError`. `readBackupCounts` and `readUnsyncedIds` exclude assets with a `syncError` (`assetsRepository.ts`), so "unsynced" undercounts photos that never uploaded. `useBackupCounts` reports zeros while `!isAuthenticated`, and `SettingsScreen` shows nothing but the login form when signed out (todo: "Uploads during an account switch").
- **Server.** `authenticate` verifies the JWT and sets `request.userId` without a user lookup; the storage routes look the user up themselves (`storageFor` → 401), the sync routes don't (an unknown user id hits the FK and answers 500). `rotateRefreshToken` deletes the presented token in the same transaction: a refresh whose response is lost (timeout after the server committed) leaves the client with a token the server no longer knows, and the next refresh signs it out. Nothing identifies a server: `/up` returns `{ status: 'ok' }`.
- **Other device state.** AsyncStorage: `user` (`features/cloud/user/*`), `app-settings`, the AI keys of `aiSuggestionsStorage.js`. Sentry: `Sentry.init` in `App.js`, `captureException` in `BootErrorBoundary`, `AppInit` and the thumbnail loader; no user scope. Tests: `accountSwitch.test.ts` pins today's wipe; `refreshAccessToken.test.ts` mocks the two-key store with `vi.mock`; server `tokens.test.ts`, `routes.auth.test.ts`, `health.test.ts`; `apps/server/test/setup.ts` provides the config env. The web preview (`scripts/webPreview.mjs`) logs in over HTTP and `addInitScript` writes the two localStorage keys on _every_ navigation, reload included.
- **expo-sqlite 55.0.20, same API on both platforms.** `openDatabaseAsync(name)`, `closeAsync()`, `deleteDatabaseAsync(name)`. Both platforms share one native handle per path unless `useNewConnection` (`findCachedDatabase` in `web/worker.ts` and `ios/SQLiteModule.swift`); iOS refcounts it (`closeAsync` closes when the last holder releases), web closes it for every holder at the first `close`. iOS `deleteDatabase` throws while the database is open and when the file is missing; web's has no open check (`vfs.jDelete`). Web runs wa-sqlite on an `AccessHandlePoolVFS` with a fixed pool of 6 OPFS access handles (`DEFAULT_CAPACITY`, nothing calls `addCapacity`): **every existing file takes a slot, open or closed**, until it is deleted, and a rollback journal or temp file takes one while it exists. A second connection or `ATTACH` to an existing file costs no slot. The `directory` argument is unsupported on web, so names stay flat. drizzle's `migrate` keeps `__drizzle_migrations` per database, so each library migrates itself.

## 1. The model

### 1.1 Owner, library, registry, session

```ts
type Owner = { kind: 'device' } | { kind: 'account'; serverId: string | null; userId: string; email: string };
interface Library {
  id: string;
  owner: Owner;
  closed?: { pendingCount: number; atRiskCount: number; at: number };
  mergedInto?: string;
}
// registry: { libraries: Library[] }   one JSON value in AsyncStorage
// session:  { serverId, userId, email, apiBaseUrl, tokens: { accessToken, refreshToken } | null } | null
```

- **Paths come from the id**, never from stored strings: `libraryPaths(id)` is pure; `id === 'squidbox'` (the migrated library) maps to `squidbox.db`, `assetfiles/`, `assetthumbnails/`; any other id (a uuid) to `library-<id>.db` and `libraries/<id>/{files,thumbnails}/`. `removeLibrary` asserts the id's shape (`/^[a-z0-9-]+$/`) and only ever deletes those derived paths, so no registry content can name a path. The owner is also written into each database's `sync_meta` (`owner`, JSON) when a library is created or migrated, so the registry is rebuildable (§1.6).
- **The registry** is one JSON value, kept as one in-memory copy and changed only through `update(fn)` on a promise chain, so concurrent writers (the boot's `/me` resolving a `serverId`, a switch, a merge marker) never lose an update. A value that doesn't parse is never treated as "no registry" and never reaches `BootErrorBoundary` (whose message says "reinstall", which would delete every library): it is moved aside (`libraries.corrupt-<timestamp>`) and `rebuildRegistry` recreates the list from the owners stored in the databases (§1.6). It holds no `openId`, no timestamps: `closed` is for display only, `mergedInto` is the merge marker (§1.5 (f)). There is at most one device library, created on demand.
- **The session is the open pointer.** No session → the device library is open. A session → its owner's library is open (`findAccountLibrary(serverId, userId)`, created if missing). `tokens: null` → `needsReauth`: the library stays open, nothing syncs. `isAuthenticated` = the session has tokens, is verified for `API_BASE_URL` (§1.3) and matches the open library's owner (`sessionMatches(library, session)`, pure, tested). One session at a time; a parked library has none and re-signing into it asks for the password (§6, decision 7). The session lives as one JSON value under `session` in SecureStore (native, `AFTER_FIRST_UNLOCK` as today) and localStorage (web); one write per change, so a refresh persists both tokens atomically.
- **Per library**: the SQLite database (collections, outbox, `sync_meta` with cursor, status, `firstSyncDone`, `sync_log`, the Inspector that reads them), the two folders, the in-memory `webThumbnailUrls` map (cleared on a switch) and the thumbnail loader's queue (remounted). `lastSyncUserId` retires (left unread in `sync_meta`). **Global**: registry, session, `app-settings`, the AI model, prompts and chat history (a scratch conversation, §6), Sentry (unchanged), the downloads cache.

Built as: `src/library/{libraryPaths,owner,registry,rebuildRegistry,current,switchLibrary,bootLibrary,sessionLibrary,sessionMatches,sameAccount,currentSyncIdentity,mergeLibrary,mergeRun,removeLibrary,fs(.web)}.ts`, `LibraryProvider.js`, `SwitchingScreen.jsx`; `src/utils/cloud-api/{sessionStore,requireSession,sessionIdentity,SessionChangedError,initializeCloudAsync}.js`; `src/sync/backupRun.ts`; `features/cloud/confirmSignOutAsync.js`. `atRiskCount.ts` went with the simplified UX.

`src/library` is TypeScript and joins `tsconfig.synccheck.json`'s `include`. Only the database opener is injected (`openDb(name) => Promise<AppDb>`, as the engine injects db and transport); the thin storage and file-system modules (`sessionStore`, the registry's AsyncStorage access, `fs.ts` wrapping `expo-file-system`) are mocked with `vi.mock` in the tests, as `test/refreshAccessToken.test.ts` does today. `sync/db/client.ts` keeps `getDb()` and gains two functions with different jobs: **`openAppDb(dbName)`** only opens a database, runs `PRAGMA cache_size` and drizzle's `migrate(db, migrations)` (`drizzle-orm/expo-sqlite/migrator`, the function behind today's `useMigrations`, which already runs on the sqlite-proxy db), and returns an `AppDb` that the caller closes; it never touches the global. `openLibrary(library)` in `current.ts` is the only code that calls `openAppDb` and sets the database behind `getDb()`; `closeLibrary()` clears it. Everything that inspects _another_ database (the Remove recount, the merge's source, `rebuildRegistry`) uses `openAppDb` and closes what it opened, so nothing can swap the database under the mounted app. `databaseExists(dbName)` says whether a database is really there: a file check on iOS; on web (no listing, and opening creates the file) it opens the name, looks for `__drizzle_migrations` in `sqlite_master`, and closes and deletes the file when the table is missing, so a probe never leaves an empty file in a slot. Close is a queued unit of the driver (`AppDb.close()`: waits for the queue, closes the connection; every statement queued after it rejects with "The database is closed"). The 33 `getDb()` call sites keep their one-liner. The file helpers read `getLibrary()`'s paths instead of the two constants; code whose work outlives a screen captures the library once at its start and passes the paths on (`buildAssetAsync` resolves `libraryPaths` before the move, `preloadAssetThumbnailsAsync` before its network call, `backupRun` at its start), so a late write fails against a closed library instead of landing in the next one.

### 1.3 Server identity and session binding

The server reports a stable **`serverId`** (`SERVER_ID` in its config, §2) in `GET /up`, in the login response and in `GET /me`. The session records the `apiBaseUrl` it was obtained from. **With the same base URL and a complete session (`userId`, `serverId`, tokens) the app is authenticated at once, offline included.** Otherwise `initializeCloudAsync` resolves it: a changed base URL → `GET /up` (unauthenticated) first, the session is used only when the reported `serverId` matches (`apiBaseUrl` rebinds), else it is dropped (the library stays, `needsReauth`); a session missing `userId`, `serverId` or `email` (the migration, §1.6) → `GET /me` fills them, a 401/403 sets `tokens: null`, a network error leaves it for the next launch. So a token never goes to a base URL that hasn't proven it is the session's server, and a new dev tunnel host doesn't cost a login; a production build's base URL never changes.

### 1.4 Opening, closing, switching

Boot: `LibraryProvider` (above `CloudProvider`) reads the registry (running `rebuildRegistry` once when there is none, §1.6) and the session, and opens the open pointer's library at once, without the network (the device library when there is no session; a migrated session without `userId` opens the account library whose `serverId` is still null, there is at most one). `initializeCloudAsync` verifies the session concurrently (§1.3); `isAuthenticated` turns true only when that passes and sync starts only then, so the open library needs no switch whatever the outcome. That also closes the "Start cloud init while the database opens" todo.

`switchLibrary(target)` lives in `LibraryProvider`: it sets `next`; `LibraryGate` (below `AppInit`, replacing `DatabaseGate` + `MigrationGate`) renders a small switching screen ("Opening your library…" as built, planned as "Opening <label>…"; an `ActivityIndicator` on the app gradient like `FirstSyncScreen`) while `next` is set, so every consumer below unmounts and its effect cleanup runs (`watchQuery.stop()`, the thumbnail loader's refs, the backup run's abort); the provider's own effect on `[next]` runs in that same commit, after those cleanups, and performs the switch, then sets `library` and the gate remounts the tree under `key={library.id}`. The remount resets navigation, so the switch ends with `navigateToTab('SettingsTab')` (queued until the container is ready, which `navigationRef.js` already does). `switchLibrary` resolves once the new library is open, and `CloudProvider` sets its state after it. The switch runs inside `withSyncPaused`, which now **aborts** the running sync (§1.7) instead of waiting for it: abort the backup run and wait for it; snapshot the closing library's `pendingCount` (outbox count) and `atRiskCount` for display; `closeLibrary()`; clear `webThumbnailUrls`; `openLibrary(target)` and create its two folders. If opening the target fails (web's slot limit, §1.8, or any error): a target that was being _created_ has its half-made file deleted (`deleteDatabaseAsync`, so it keeps no slot), the session reverts to the previous owner's (the one that was just closed, with its tokens; for a sign-out that failed to open the device library, the old session stays), the previous library reopens, and the user sees an Alert; the registry entry of a library that never opened is removed. Sign-in, sign-out and expiry change the session inside the same section, so a sync run never spans a session or library change.

### 1.5 The flows

- **(a) Session expired.** A rejected refresh sets `tokens: null` (nothing else changes: the library stays open and editable, writes queue in its outbox) and alerts "Sign in to keep syncing" / "Your session for <email> ended. Your changes are saved on this iPhone and will upload after you sign in." / Not Now · Sign In (→ Settings). While `needsReauth`: Settings' Account section shows "Sign in to sync · N changes, M photos waiting" (N = `pendingCount`, M = the at-risk photo count) above the `LoginForm` with the owner's email pre-filled and a "Sign in as someone else" link that clears it (then the login is (c)); the Backup & Sync rows stay visible with their live counts (`useBackupCounts` drops its `isAuthenticated` gate; the run still needs the session); the header avatar (`FloatingHeader`) shows the needs-attention state. Thumbnails that aren't on the phone can't load (the loader pumps only while `isAuthenticated`): the loader exposes `isActive`, and `AssetImage` shows a still placeholder instead of the pulse while it is inactive. Re-signing in as the owner restores the tokens and sync pushes the outbox.
- **(b) Explicit sign-out.** "Sign out" opens an action sheet (`ActionSheetProvider` is mounted; `Album.jsx` is the pattern) titled from a fresh count (`atRiskCount` + `pendingCount` of the open database: "3 changes and 12 photos haven't synced yet", or "Everything is synced"), options "Keep on This iPhone" (default), "Remove from This iPhone" (destructive; with anything at risk a second Alert "Remove 3 unsynced changes and 12 photos?"), Cancel. Both options first clear the session locally and switch to the device library (§1.4), then revoke the refresh token through plain `api` as best effort outside the paused section (it can take the 15 s timeout offline); Remove then runs `removeLibrary(parked)`. `confirmLogoutAsync` goes. The text is truthful at every step: in step 2, before libraries exist, the Alert already says "Your library stays on this iPhone."
- **(c) Sign-in as another account.** Login returns `{ serverId, user }`; the session changes and `switchLibrary` opens `findAccountLibrary` → the parked library (its outbox pushes on the next sync) or a new empty one; A's library is parked untouched. `confirmLoginAsync` goes. Settings gets "Libraries on this iPhone": one row per library (label: email or the device label; value: "N pending · M at risk" from `closed`, live for the open one, which is marked "Open"); sizes are measured lazily when the section shows (`getInfoAsync(dir, { size: true })` recurses on iOS; it never runs during a switch) and only if that measures fast (§6, decision 10). Tap on a parked one → Alert with Remove (destructive). **Remove never trusts the snapshot**: it opens the parked database with `openAppDb` (not the open library's slot), recounts `atRiskCount` and `pendingCount`, closes it, and confirms with those numbers (a crash can leave `closed` stale). The open library is removed only through (b).
- **(d) Backends.** §1.3 and §2. Two servers with the same user id are two libraries. The migrated library's `serverId` is null until the first `/me` or login for its `userId` resolves it (§1.6).
- **(f) A local-only user signs in to an existing account.** After the account library's first sync has drained (so duplicates can be seen), if the device library holds records and no answer was given for this sign-in, `planMerge(source, target)` dry-runs the rules below and one Alert shows its result: "Add N photos, M albums and P posts from This iPhone to <email>?" (plus "K photos are already in the account" / "K photos are in another account's storage and stay here" when non-zero) / Keep Separate · Add to Account. Add runs behind `showBlocking` (no Cancel; device libraries are small) in three resumable stages:
  1. `applyMerge`: the source is opened with `openAppDb` (a second connection; on web an existing file costs no new slot), and **all records copy in one transaction** of the target through `saveRecords(…, { isNew: true })` (each copied record gets its outbox row). Rules: a record whose `id` exists in the target is skipped, but if the source has an outbox row for it, that payload is enqueued with its _own_ `updatedAt` (not bumped), and only when the target has no outbox row for that record or the source payload's `updatedAt` is newer (`enqueueMutations` keeps one row per record and would otherwise overwrite a newer pending edit), so the server's LWW settles it; an asset whose `mediaLibraryAssetId` exists live in the target is skipped and the id map points its edges at the existing asset, with `isFavorite` merged as OR and differing `notes` appended to the target's; an asset with `isFileSynced` and no local file is skipped (it lives in another account's storage) and counted; albums with `smartAlbumType` are skipped (the account has its own); same-name albums are kept separate; edges whose asset or parent was skipped for being deleted are dropped. The registry marker `source.mergedInto = target.id` is written before the transaction and **cleared again if `applyMerge` throws**; a marker alone never authorizes a removal (stage 3).
  2. `moveMergedFiles`: driven by the **target's** state, never blind, and only for assets copied **with the same id** (an asset matched by `mediaLibraryAssetId` keeps the target's own file, whose filename and extension may differ): for each such asset, if the target lacks the file (or thumbnail) and the source has it, check the source path exists, then move it (a move only ever happens into a missing destination, so a second run can't delete a moved file). Nothing about the mapping is persisted: a resume re-derives it from `planMerge(source, target)`. Boot resumes this pass for any library with `mergedInto` set.
  3. The source library is removed (decision 5) only when **both** `planMerge(source, target)` reports nothing left to add (every source record is in the target by id, or skipped by a rule that leaves nothing behind: a `mediaLibraryAssetId` duplicate, a smart album, a dropped edge) **and** the file pass found nothing left to move. A crash or throw between the marker and the commit therefore leaves the source intact: the resume finds everything still to add and stops (the marker stays until the user answers the dialog again, which runs stage 1 again). Cloud-only assets (skipped, "stay here") are the one rule that leaves something behind: with any of them the source is kept and the dialog says so. The marker lives for seconds in the normal case.
     Keep Separate leaves the device library parked; it shows in "Libraries on this iPhone".
- **(g) A local-only user creates a new account.** There is no sign-up endpoint (accounts are seeded), so (g) is (f) against an empty account: the first sync pulls nothing, the dialog asks, Add copies everything. One code path.
- **(h) Sign-out returns to the device library** (both sheet options), created empty if missing.

### 1.6 Migration of existing installs

`rebuildRegistry` runs when the registry is missing or was moved aside (first launch after step 4a, a lost or corrupt registry value). On iOS it lists `SQLite/` for `squidbox.db` and `library-*.db`; on web (no listing) it probes `squidbox.db` with `databaseExists` (§1.2), which deletes the empty file a probe creates, so a fresh web install ends with no `squidbox.db` and the `'squidbox'` id only ever names a migrated install. Each database found is opened with `openAppDb` (migrated) and closed again, its `owner` read from `sync_meta` if present; `squidbox.db` without one (today's install) gets its owner from `lastSyncUserId`: set → `{ kind: 'account', serverId: null, userId, email }` with the email from the session when its `userId` matches, else `''` (filled by `/me`); not set → `{ kind: 'device' }`, with or without rows (the "unknown owner" case folded into the device library, §6 decision 4; the merge's id rule makes the one risky case safe: data that was in fact that account's, from a build between `3f616f0` and `43c1bdf`, is skipped record by record because the account library already holds the same ids after its first pull). The owner is then written into `sync_meta`. When the migrated library gets an account owner and there is **no session** (a user who signed out before the update: today they see their library, signed out), the rebuild writes a token-less session `{ serverId: null, userId, email, apiBaseUrl, tokens: null }`, so they boot into their data with `needsReauth` instead of an empty device library (there is no Libraries UI before step 5 to get it back otherwise). A fresh install has no `squidbox.db`; the device library is created on demand as `library-<uuid>.db`.

The session conversion happens in step 2, before libraries: the first `getSession()` that finds the old keys writes the new value (`serverId: null`, `userId`/`email` from the stored `user` when present, else `null` until `/me` fills them, the `handleMissingUser` case) **first, then deletes the old keys** and the `user` key. Nothing is moved, renamed or deleted on disk, so a crash at any point re-runs to the same state. Users lose nothing: the same database, the same folders, a session that keeps working. **No downgrades past step 4a**: an older build opens `squidbox.db` with its wipe-on-switch logic and knows nothing of `library-*.db` (owner checklist).

### 1.7 Phase-1 safeguards, under this model

- **Sync runs are abortable and bound.** `runSyncOnce(db, transport, { signal })` (planned as `{ shouldStop }`) checks the abort signal between push batches and between applied pull batches (the cursor commits per batch, so a resumed pull continues where it stopped); `withSyncPaused` requests the stop and waits, so a sign-out on `FirstSyncScreen` waits for one batch, not the pull. `withSyncRun` captures the **identity** `{ libraryId, serverId, userId }` at its start, refuses to run unless `sessionMatches` (so the trailing re-run of `singleFlight` can't run on the next library: a device library with a stored session syncs nothing), and builds the transport for that identity (`httpTransport(identity)`): every request reads the tokens fresh from the session store and is refused when the stored session's identity differs, so a long run uses the tokens a mid-run refresh rotated, never a captured pair.
- **Backup run** (`sync/backupRun.ts`, the loop out of `CloudSyncProvider`, which keeps the progress state): `runBackup(db, ids, { upload, isCurrent, onProgress })` captures the identity `{ libraryId, serverId, userId }` and stops before each asset, between an upload and its `updateAsset`/`deleteAssetFileAsync`, and before the thumbnail upload when `isCurrent()` turns false, without `syncError` and without deleting the file; an upload in flight is cancelled (`uploadTask.cancelAsync()`, the TODO in `uploadFileAsync`). `uploadFileAsync(filename, uri, identity, onProgress)` reads the access token fresh for the identity it was given (refused when the stored session is someone else's); its 401 retry calls `refreshAccessTokenAsync(identity)`, which refreshes only while the stored session is still that user's and otherwise throws `SessionChanged`; `apiWithAuthentication` does the same (the request interceptor notes the identity on the config and reads the token fresh, the response interceptor refreshes against that identity). "Never refresh into a different user" is one check in one place.
- **`logoutAsync`** posts `/auth/logout` through plain `api` with the refresh token it was given (the route needs no auth, §0), best effort (§1.5 (b)).
- **`initializeCloudAsync`** clears tokens only on a 401/403 from `/me`, or drops the session when `/up` reports another server (§1.3); a network error keeps it.
- **`refreshAccessTokenAsync`** writes the session once (both tokens) and keeps today's single-flight and "a newer sign-in replaced the session" guard.
- **Server** (§2): refresh-token grace, `authenticate` rejects unknown users.
- **Counts stay visible while `needsReauth`** ((a)); **sign-out text is truthful and recounted** ((b)); **orphaned files** are gone because files live in the library's folders and leave with it.

### 1.8 Web

Same code: expo-sqlite named databases on both platforms, one open at a time, two during a merge (the source is an existing file: no new slot). The registry and session use AsyncStorage/localStorage. The file helpers aren't called on web (`webThumbnailUrls` stands in). **Web library limit**: the OPFS pool has 6 fixed slots and every library file keeps one, so after the open library, its journal and a temp file, about three parked libraries fit; a fourth library fails while `openAppDb` migrates it (its journal gets no slot), and the half-created file would keep a slot and starve even the current library's journal, so `switchLibrary` deletes it, reverts the session and reopens the previous library (§1.4) and shows an Alert ("This browser can't hold more libraries. Remove one under Libraries on this device."). The web `deleteDatabase` has no open check, so `removeLibrary` asserts the library isn't open before deleting on both platforms. `scripts/webPreview.mjs` writes the session record **only when its own marker `webPreviewSeeded` is absent** and sets the marker (`addInitScript` runs on every navigation; writing on every load would restore a refresh token a rotation has already revoked, and "write when no session exists" would re-seed right after a check deletes the session) with `serverId` from the login response and `apiBaseUrl: 'http://localhost:8081/api/v1'` (the page's origin, what `apiBaseUrl.js` computes on web; `localhost:3100` stays the script's own login URL). Boot then creates the account library and syncs it, as a restored session does on a device, so `openWebPreview()` and `settleAsync` keep working for every existing script. Each preview run is a fresh browser context, so the fresh-install path runs on every preview.

## 2. Server

- `SERVER_ID`: a uuid in `config.ts` (required; `.env.docker` gets a fixed one for `dev:local`, `apps/server/test/setup.ts` a test value; the Fly secret is set with `fly secrets set` **before** the deploy, since `loadConfig` fails boot without it). Reported by `GET /up` (`{ status, serverId }`), `POST /auth/login` (`{ …, serverId }`) and `GET /me` (`{ user, serverId }`); the shared contracts (`packages/shared/contracts/auth.ts`) add the field. The app ignores unknown fields, so the server ships first (the rule from sync-design §6).
- `authenticate` loads the user once into `request.user` (`findUserById`; `AppError.unauthorized` when missing), and `storageFor` and `/me` reuse it instead of looking it up again.
- Refresh-token grace, bounded: a rotated token's **predecessor stays valid for 10 minutes (`ROTATION_GRACE_MS`), until its successor is first presented**. `refresh_tokens` gains `replaced_by text` (migration 0005) and `replaced_at timestamptz` (migration 0006). Rotate = `UPDATE … SET replaced_by = <new>, replaced_at = now() WHERE token = <presented> AND replaced_by IS NULL AND expires_at > now() RETURNING user_id`, then insert the successor; when no row comes back, read the presented row: if it was rotated within the grace and its `replaced_by` successor row exists with `replaced_by IS NULL` and `expires_at > now()`, return that successor again (and a fresh access token); otherwise 401 (unknown, expired, retired, or a successor that was already rotated). Presenting a successor deletes its predecessor (`DELETE WHERE replaced_by = <presented>`). Two concurrent refreshes of one token get the same successor; a lost response is retried safely within the window; after it the client lands in `needsReauth`, which loses no data. `revokeRefreshToken` deletes the presented token, its predecessor and its successor. Tests in `tokens.test.ts` (Postgres, `npm run test:db`) and `routes.auth.test.ts`.

## 6. Open decisions (recommendation first)

1. **Is the device library visible to a signed-in user?** Recommend: listed in "Libraries on this iPhone" only when it holds records, not openable from there (§4). Alternative: always listed.
2. **The device label.** Recommend `libraryLabel`: "This iPhone" on iOS phones, "This iPad" on pads (`Platform.isPad`), "This device" on web. Alternative: "This device" everywhere.
3. **What Settings shows when signed out.** Recommend: the login form under "Account", the Libraries section, the AI and Data sections as today, Backup & Sync hidden. Alternative: show Backup & Sync greyed with "Sign in to back up".
4. **"Unknown owner".** Recommend folding it into the device library (§1.6). Alternative: a third owner kind with its own label and a dedicated "Is this <email>'s library?" dialog.
5. **When the device library is removed after Add to Account.** Recommend: as soon as the file pass finds nothing left (§1.5 (f) stage 3): the records are then durably in the account library's outbox and the files in its folders, exactly where a locally added photo lives before its upload, and the account library's own counts show what is left to push and back up. Keeping it until push and backup complete means a `merging` state that can linger for weeks (backup is manual).
6. **Keep Separate: remember it?** Recommend asking once per sign-in into that account; a later merge from the Libraries list is §4. Alternative: persist `keepSeparateFrom` on the device library.
7. **One session or one per library.** Recommend one (§1.1). Alternative: keep each library's refresh token so switching accounts is a tap; more state to keep valid and to revoke.
8. **Where the reauth marker lives.** Recommend the Settings row plus the header avatar state. Alternative: a banner on every screen.
9. **`SERVER_ID` source.** Recommend the env/secret (§2). Alternative: a `server_settings` row generated at migrate.
10. **Directory size in the Libraries list.** Recommend measuring lazily when the section shows and only if it measures fast at 10k files on device; otherwise counts only.
11. **Do deleted (tombstoned) assets count as at risk?** Recommend no: a tombstone with an un-uploaded file is a photo the user chose to delete; its outbox row (if any) still counts as a pending change. Alternative: count them, since "Delete permanently" doesn't exist yet.

## 7. Risks and checks

- **Web OPFS slots** (§1.8): about three parked libraries; the limit surfaces as an Alert on the switch, never as data loss, and `removeLibrary` frees the slot (`jDelete`). The merge's second connection and the journal fit (open 1 + journal 1 + source 1 + a temp file).
- **Closing under load.** A read already in the driver queue when `close()` is queued still runs before it (FIFO), so nothing reads a closed connection; a statement queued after it rejects, which a stopped watch only logs (`watchQuery` catches). Work captured per library (§1.2) fails on the closed handle instead of writing into the next library. `driver.test` pins both.
- **Shared native handles.** The library module is the only opener and never opens a name it hasn't closed (the merge opens a _different_ name); iOS refcounts, web closes for all, and with one holder per name both behave the same. `removeLibrary` asserts "not open" itself (web has no check) and tolerates a missing file (iOS throws).
- **The install migration on the owner's phone** runs once and moves nothing; a device check before the build goes out (step 4a); no downgrades past 4a.
- **The merge** copies in one transaction, so a crash leaves the target untouched or complete; the file pass is idempotent by construction (moves only into missing destinations, same-id assets only) and resumed from the marker; the marker alone never removes anything: removal needs `planMerge` to report nothing left to add and the pass nothing left to move, so a crash before the commit keeps the whole device library. The `/me` that resolves a migrated `serverId` can fail offline: `sessionMatches` treats a null `serverId` on both sides as a match for the same `userId`, and `findAccountLibrary` treats a library's null `serverId` as matching its `userId` until resolved.
- **Backup abort granularity.** An upload in flight is cancelled; the server may still complete a multipart upload it had received. The file then exists in A's storage with the record not marked, and the next run uploads it again to the same key: harmless (sync-design §4's argument).
- **Sync abort granularity.** A stop lands within one push batch (500 mutations) or one applied pull batch (≈5,000 records, a few seconds on web); the switching screen covers that wait.
- **Sessions bound to the base URL** cost one `/up` per changed dev tunnel; a production build never pays it.
- **`FirstSyncScreen` under `needsReauth`**: a library whose first sync never drained and whose session expired shows the app with the marker rather than the setup screen; re-signing in resumes the pull from its committed cursor.
- **Measurements**: a switch (close + open + migrate of an already-migrated db) should stay under 300 ms on device and 1 s on web; `removeLibrary` of 10k files runs behind the overlay; the merge copies at `saveRecords` speed (a few statements per 500 records, sync-design §8). Record them in the todo's device-check entry.
