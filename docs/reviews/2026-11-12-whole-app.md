Scope: `apps/mobile/src`, `apps/server/src`, `packages/shared`, at `fb69b03` on `claude/project-thread-phrqo8` (main plus the review skill). First run: no earlier report in `docs/reviews/`, so there is no Outcomes section. ## The three questions

**What actually went wrong?** The last five merged PRs (#78 to #82) were small and none was reverted, but #81 (starred albums) shows the pattern that costs the most: one new field (`favoritedAt`) landed in six files because a record's defaults are hand-kept per provider, per test factory and in the mock seed, and the one copy that was missed (the server test helper) was caught only by a failed CI run. The same PR copied the "favoritedAt follows isFavorite" rule a third time, into a repository that lives inside a feature folder instead of `sync/`, and gave the shared name-and-notes edit sheet an album-only Starred switch. #78 added a sheet route and a layout line per group, which nothing checks. The three cold agents each stalled on the same thing: the rule that would have told them where a cascade, an ordered membership or a synced setting lives is nowhere in CLAUDE.md or the design doc, only in one file's comment or one provider's `useMemo`.

**What could still go badly wrong?** Six of the eight failure scenarios ran green against the real repositories and the two-device harness (offline edits on two devices, replayed and reordered operations, interrupted uploads and an account switch, an older app version pulling newer data, migrations over old rows). Two did not: restoring a deleted contact brings it back without its lists and photo links, because the delete tombstones the edges and the restore only clears the contact's own tombstone (run, loss confirmed), and a contact restored after its tombstone was pushed names a photo the user's storage never received (traced). Nothing in the UI loses data: every delete but one confirms, and the sheets' discard guard held on every screen driven.

**What makes the next change unnecessarily difficult?** Read queries live half in `features/<x>-list` and half in `sync/`, so 45 of the 103 lines that reach into another feature's internals are features reading a list feature's query. Nine provider folders are "features" that `components`, `hooks`, `utils` and `sync` import upward (24 lines). On the UI side the same act has several shapes: seven delete confirms, two label conventions for menus, 16 Title Case labels among ~180 sentence-case ones, "Assets" as a user-facing noun, three formats for "ago", 33 raw `Text` and 21 raw `Pressable` sites in features, and the component gallery (the design-system contract) shows none of the sheets, floating bars or status screens, so an agent copies the nearest feature's variant instead.

## Risks

### R1 · Restoring a contact loses its list memberships and photo links — risk, M, OPEN

- Location: `apps/mobile/src/features/contacts-context/ContactsProvider.tsx:123-131` (`setContactDeleted` tombstones `contact_list_members` and `contact_links`; `restoreContact` clears only the contact's `deletedAt`), `features/contact-list-detail/ContactList.tsx:63-68` (the Restore row).
- Rule: `docs/sync-design.md` §7 "Deleting or purging an asset does not touch its edges, so a restore puts it back where it was" is the only restore rule the design has; the code's comment at `:129-130` chose otherwise for contacts, in code only. The delete alert ("They leave your lists and the photos, albums and posts they are on") describes the delete, not the restore.
- Evidence: throwaway run of scenario 7: after restore, `member deletedAt=1794467636922`, `link deletedAt=1794467636923`, contact `deletedAt=null`.
- Cost: a tap on a Deleted row brings the contact back stripped of every photo tag and list, with no confirm and no way back but re-tagging each photo; the tombstoned edges sync, so every device loses them.
- Fix: first decide the rule in §10 (restore puts the contact back where it was, as for assets, is the consistent one). Then `setContactDeleted` tombstones the edges at the contact's own `deletedAt` clock and `restoreContact` restores exactly the edges whose `deletedAt` equals it (a membership removed on purpose before the delete carries another clock and stays out), in one transaction.
- Bounded by the review rule: the fix changes what synced data means (which edges a restore revives), so this run ships only the reproducing test, `test/contactsRepository.test.ts` "restoring a deleted contact puts it back in its lists and on its photos", marked `it.fails` until the fix lands; `docs/sync-design.md` §10 says the edge rule is open. The fix is decision 1.
- Seen next run: `test/contactsRestore.test.ts` "restoring a deleted contact puts it back in its lists and on its photos" passes without the expected-failure mark.
- Files: `ContactsProvider.tsx`, `docs/sync-design.md` §10, `test/contactsRestore.test.ts`. Size M. Test: the one above (fails before, passes after).

### R2 · A contact deleted before its photo uploaded pushed a tombstone naming a file the storage never got — risk, S, FIXED

- Location (before the fix): `apps/mobile/src/sync/worker.ts:168` (`filesToUpload` returned nothing for a `delete` row), so a contact made with a photo and deleted before any sync pushed a tombstone naming `avatar-….jpg` that storage never received; a restore then showed the photo as missing on every other device, with no error anywhere.
- Rule: §6 "A pushed live record never names a file the user's storage doesn't hold", whose own caveat ("a Restore, when it comes, must treat a named file as possibly missing") was the gap.
- Fix: a `delete` row uploads the files its changed fields name like any other row, so no pushed record, live or deleted, names a file the storage lacks, and a restore on any device finds it (§6 now says so, the caveat is gone). A first version fixed it at restore time by re-sending the photo this device holds; the correctness review showed that version let a stale photo beat a newer one set on another device before the delete, and that it uploaded on every restore, so the fix moved to the push. The restore itself is now one `makeRepository.restore` for assets and contacts (clears `deletedAt`, skips live rows).
- Verified: `test/workerFileFields.test.ts` "a contact deleted before its photo uploaded uploads it before the tombstone's push": red with the early return in place (`calls` was `['push contacts avatar-x-1.jpg']`, no upload), green without it (`['upload contacts.avatarFilename avatar-x-1.jpg', 'push contacts avatar-x-1.jpg']`); both runs quoted in the PR. The sibling case "a tombstone of a pushed contact uploads nothing" extends the existing "uploads nothing" test.
- Left as is: tombstones pushed by earlier builds that already name a missing file are not healed. A refused or failed upload now holds a tombstone's push back with the error, like any row.
