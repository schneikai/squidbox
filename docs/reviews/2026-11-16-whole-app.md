## 1. The three questions

**What went wrong (PRs #131, #133, #134, #135, #136).**
- Branches built on work that was being replaced:
  - #131, #133 and #134 built on mentions, copies and channel versions while the open #135 was replacing all three. Their work was thrown away within a day.
  - #135 spent at least eight commits removing or re-bending it (F50).
- Shared behaviour was re-homed after it was written: six move commits over three PRs (F1, F37).
  - Once, the next user didn't find the helper and shipped a web bug to the branch (the suggestion press in #133).
- Tests named for a rule passed with the rule removed: the readMentions order and the deleted-copy lock (R3).
- One "starts a word" rule is written in five places and was fixed one copy at a time in five commits of #135. The copies still disagree (F3).

- The mention line of the answer format shipped untried against the production writing model and needed its own PR, #136, the same evening (R8).

**What could still go badly wrong.**
- Every deploy drops and recreates the `server_seq` triggers in separate commits while the old server takes pushes. In a throwaway run, a push in that window was `applied` but never pulled by any device (R1).
- Per-channel copies (#135) don't group `sentAt` with `posts`. A device that hasn't seen a send can replace the sent text with text that was never sent, and the copy still shows as sent (R2).
- Behind those two, several data rules have no test that fails when they break:
  - local-only fields reaching the outbox;
  - a write losing its transaction (caught by 1 seed in 60);
  - the deleted-copy lock;
  - the middle installed build (R3).
- Account scope:
  - Each server read of a per-user record keeps the account boundary by one hand-written filter, and push accepts a per-user record under any id.
  - Removing readPersona's filter keeps all 538 server tests green (R4).
- `mergeLibrary` lists collections by hand in five places. A collection missing from those lists is deleted with the source library (R5).
- Smaller risks:
  - one tap removes a contact's photo (R6);
  - two of four path builders join a synced file name unchecked (R7).

**What makes the next change unnecessarily difficult.**
- Where code lives (D1):
  - Features reach into each other's internals: 182 lines over 72 pairs, 4 of them two-way (F1).
  - Read queries have three homes again (F6), and shared helpers two (F16).
- Writes:
  - Whether a write syncs is decided at each of 33 call sites (F2).
  - A failure is reported by hand at 26 catches (F4) and turned into text by hand at 12 more (F5).
- About a dozen rules are written again beside their first copy: favoritedAt, overrides, the tagged SQL, the placeholder syntax and more (F3).
- The UI text has no one voice: nouns, confirm titles, alert titles and Title Case (F8, D2).
- 21 smaller classes each cost one wrong turn per change in their area.

### R1 · A push made during a deploy's trigger rebuild is applied but never pulled — OPEN
- Class: the `server_seq` trigger of every collection is dropped and recreated in separate autocommit statements while the old machines take pushes; a write in between gets no `server_seq` and no device ever pulls it.
- Sites: 
  - from data-integrity "### 1.": apps/server/src/db/migrate.ts:25-33 (DROP TRIGGER, then CREATE TRIGGER, autocommit, per collection, 18 tables); apps/server/src/db/schema.ts:82,136 (`server_seq` nullable, no default); apps/server/fly.toml `[deploy] release_command = "npm run migrate:prod"` (runs while the old machines serve).
  - from efficiency-server "E1 ·": `apps/server/src/db/migrate.ts:25-32` (`DROP TRIGGER IF EXISTS` then `CREATE TRIGGER`, one `db.execute` each, per collection; 18 collections: `grep -c ": serverCollection(" apps/server/src/sync/collections.ts`); run by `apps/server/fly.toml:18` (`release_command = "npm run migrate:prod"`, "before the new version goes live") and `ci.yml:56`.
  - `.github/workflows/ci.yml:56` (the migration runs the same way in CI)
- Rule: sync-design §3 :110-111 "A write that skips the lock reopens the visibility gap; a write that skips the trigger is never pulled."; CLAUDE.md:49 "Every installed build keeps working against today's server".
- Evidence: a throwaway DB test (DROP as migrate.ts:26, `push()` a new asset and an edit, CREATE as migrate.ts:28, `pull()`) gave `["applied","applied"]`, the new record's `server_seq` null, and the pull returned nothing for it. The scenario failed when run.
- Cost: a record or edit pushed during a deploy never reaches the other devices, not even through Rebuild from server, and the pushing device shows no error. Every deploy opens the window (18 collections, 36 statements).
- Fix: extract `ensureServerSeqTriggers(db)` that runs the sequence, function and triggers in one transaction (or `CREATE OR REPLACE TRIGGER` only where one is missing); make `server_seq` NOT NULL so a write without the trigger fails and is retried.
- Check: the new DB test below; today 0 tests cover it.
- Seen next run: the test fails if migrate.ts commits between the DROP and the CREATE.
- Files: `apps/server/src/db/migrate.ts`, a drizzle migration for NOT NULL, `apps/server/test/sync.test.ts`.
- Size: S.
- Test: run `ensureServerSeqTriggers` in an open transaction, push on another connection, commit, then assert the row has a `server_seq` and a pull from the earlier cursor returns it.
