# Plan: per-screen, SQL-backed, paged reads for Squidbox (50k+ assets)

Goal: startup time and memory stay flat as the library grows (target 50,000+ assets, iOS first; the web preview behaves the same). Criteria: SIMPLE, ROBUST, CLEAN, DRY — one data-access pattern everywhere, no caches or derived-state machinery. **[trade]** marks a little performance given up for simplicity.

Verified against the code on 2026-10-14 (after `bfae30f`, albums custom order). Baseline: `npx vitest run` in `apps/mobile` is green (96 tests).

## Selection and reorder behavior (decided)

Rule from the owner: behavior is intuitive and never silently leaves things out or adds them. Apple's apps and the HIG agree on all three points.

1. **Drag-reorder in albums works under any sort, like Reminders.** A drag under a date sort adopts the order on screen, switches the album to Custom, and the sort menu shows "Custom" at once. There's no confirmation; the date sort is one tap away in the menu. `reorderAlbumAssets(album, { assetId, afterId, beforeId })` does it in one transaction: if the album isn't on custom order yet, `edges.reorder(tx, albumId, await q.ids(tx))` writes the shown order once (it skips unchanged positions; reorder is off under a filter or search, so `q` is the album's full order); then `edges.move` writes one `keyBetween` position, and the album gets `sortOrder: 'custom'`. Every later drag is a one-row write. Smart albums and an active filter or search still disable reorder (`Album.jsx` `reorderEnabled`, unchanged). ([Reminders](https://support.apple.com/guide/reminders/remn922d0b42/mac): "If you drag a reminder in a list that's sorted automatically, the sort option for the list changes to Manual.")
2. **Select all has no cap.** It selects exactly what the current scope, filter and search show, so the header count and "N selected" are always the same number. Bulk actions confirm with the true count ("Delete 50,000 items") and run as chunked, set-based writes behind the progress overlay, with determinate progress and Cancel (HIG, Progress indicators). The writes are already set-based (`saveRecords`: a read, an upsert and an outbox insert per 500 records, one transaction per call); what's left is one transaction per 500 ids, so the queue stays responsive and cancelling between chunks keeps what's already committed (the list is live). See 1.5.
3. **Actions need a selection.** Done: download, add-to-album, post and delete are disabled without one (`SelectionActions.jsx`), and the old "nothing selected → first 500 / all" fallbacks are gone (`a23dbc0`). The Deleted album's explicit "Restore all" / "Delete all" (not in select mode) stay: they say what they do.

## 0. Diagnosis

- The providers (`features/{assets,albums,posts}-context/*Provider.js`) read whole tables through `useLiveCollectionRows/Map` → `useLiveTable` (assets, albums, posts, album_assets, post_assets) and rebuild id-keyed maps with `album.assets`, `post.assetRefs`, `postHistory`, `lastPostedAt` (`sync/derive.ts`, `deriveRecords.ts`, `useDerivedRecords.ts`). Two 50k-row tables (assets, album_assets) are read on every launch; derivations are O(library) in JS; the Albums provider recomputes every album's post history on any post or edge write.
- 40 files call `useAssets/useAlbums/usePosts`; 33 destructure a map and run `Object.values(map)` → `prepareAssets/prepareAlbums/preparePosts` (JS filter/sort/search) → id arrays → `FlatList data={ids}` with map lookups in `renderItem`. `AssetScreen` gets the whole id array in `route.params.assetIds`. `useAlbumCovers` scans every album's assets per write; `CloudSyncProvider` scans all assets per write (`getUnsyncedAssets`, `getAssetsWithSyncError`).
- `row_changes` (migration 0004: 15 triggers, `readLiveRows.ts`, `useLiveTable.ts`) exists only to refresh those maps cheaply and doubles the cost of every insert (todo: "the change-log triggers double the write cost"). Once nothing holds whole tables it has no job.
- Already there and reused, not rebuilt: `sync/useLiveQuery.ts` (`useLiveQuery(read, tables)`: coalesced re-runs on table notifications, keeps data between reads; used by `useRecordCounts`, `useSyncStatus`, `useInspector`, `FirstSyncScreen`), `sync/readByIds.ts` (rows by id, a statement per 500), `chunk.ts`/`SQL_BATCH`, batched writes (`saveRecords`/`upsertRows`), pulls applied in ~5,000-record transactions (`worker.ts` `APPLY_BATCH`), memoized `AssetGridCell` with stable handlers (`useAssetCells`), one grid setup shared by all asset grids (`useAssetCells`, `useAssetSelectionActions`, `SelectionActions`, `PickerAssetGrid`), `test/performance.test.ts` + `makeMeasuredTestDb` (counts statements, commits, rows read, full scans).

## 1. Target architecture

### 1.1 One hook, one pager, query descriptors

Nothing is held in memory globally. A screen declares what it shows as a small plain object (serializable, so it can travel in `route.params`) and reads it live:

```
sync/useLiveQuery.ts   useLiveQuery(read, tables, deps = []) → T | undefined   (existing hook, gains `deps`)
sync/usePagedQuery.ts  usePagedQuery(page, tables, deps, pageSize) → { rows, loadMore, hasMore }
```

`useLiveQuery` today re-runs `read` after a committed write to one of `tables`, never overlaps reads (`isLoading/isStale`), and keeps the last data. Add: `deps` — `read` re-runs when they change (the effect keys on `tableNames` + `JSON.stringify(deps)`); a generation counter so a result from before a deps change is dropped; the previous data stays until the new read lands (no flash to `undefined`). Rule: **`read` must be pure given `deps`** — a notification re-runs the closure captured when deps last changed. Existing callers pass no deps and keep working.

`usePagedQuery` is a growing limit on top of it:

```js
const key = JSON.stringify(deps);
const [state, setState] = useState({ key, limit: pageSize });
if (state.key !== key) setState({ key, limit: pageSize }); // reset during render: no read at the old limit
const result = useLiveQuery(() => page(getDb(), { limit: state.limit + 1 }), tables, [key, state.limit]);
const rows = result?.slice(0, state.limit);
const hasMore = result ? result.length > state.limit : false; // limit+1 keeps hasMore true after a delete
const loadMore = () => hasMore && setState({ key, limit: state.limit + pageSize });
```

Offset is always 0: first page, load-more and refresh-after-write are the same read, and the database decides the order — no append path, no offset drift, no duplicate keys. While a load-more read is in flight `hasMore` is false, so repeated `onEndReached` calls are no-ops; VirtualizedList re-checks on content-size change, so a fling chains pages. **[trade]** `loadMore` re-reads `0..limit` (3,000 rows ≈ 60–120 ms native, 3–5× on web). Escalation, inside this file only: an append path (`offset: rows.length`, refresh heals).

Query builders — pure functions of a descriptor, one file per collection, tested on better-sqlite3, exposing only what screens use:

- `features/asset-list/assetQuery.js` → `{ descriptor, page, count, ids, tables }`. Descriptor `{ scope, sort, filter, search }`: `scope` = `'library' | { albumId } | 'favorites' | 'deleted'` (the smart albums: `is_favorite = 1` / `deleted_at IS NOT NULL`; every other scope has `deleted_at IS NULL`); `sort` = `createdAt:asc|desc`, `lastPostedAt:asc|desc`, `custom` (album scope only, `ORDER BY e.position`), `random` (`ORDER BY random()`, suggestions only); `filter` ⊆ `favorites|images|videos` (`media_type`, as `useFilterAssetsAction` does today); `search` = notes substring (`LIKE '%q%'`, case-insensitive). `page(db, { limit, offset = 0 })`, `count(db)`, `ids(db)`. `tables` = `[assets]`, + `albumAssets` for an album scope, + `[postAssets, posts]` for a `lastPostedAt` sort. Double edges (`edges.add` already prevents them) are deduped by one JS line over the page.
- `features/post-list/postQuery.js` → `{ descriptor, page, count, tables }`. `scope` = `'all' | { assetId } | { albumId } | { postId } | 'repostCandidates' | 'ignored'`; `sort` = `postedAt:asc|desc` (all), `suggestRepostAt:asc` (candidates: `ORDER BY suggest_repost_at`, today's comparator), `updatedAt:desc` (ignored); `filter` ⊆ `favorites`; `search` = text substring. Keeps parsing `asset:<id>` / `album:<id>` out of `search` into a scope (as `preparePosts.js` does), so `PostsQueryProvider` and the screens that set that string are untouched. The page read is 3 statements: posts → `post_assets` of those posts → `assets` of those edges → each post gets `postAssets: [{ id, asset }]` (what `PostListItem`/`PostAssets`/`PostAssetsEditor` consume). A single post is `postQuery({ scope: { postId } }).page(db, { limit: 1 })` — no second assembly.
- `features/album-list/albumQuery.js` → `{ descriptor, page, tables }`. `scope` = `'all' | { assetIds }` (`EXISTS` on `album_assets`, for `PostAlbums`); `sort` = `custom` (default: `ORDER BY position IS NOT NULL, position, created_at DESC` — unplaced albums first, newest first, then by `position`; replaces `sortAlbumsByCustomOrder.js`, whose three test cases move to the query test), `name:asc|desc`, `createdAt:asc|desc`, `lastPostedAt:asc|desc`; `filter` ⊆ `starred|archived` (`archived` ⇒ `archived_at IS NOT NULL`, otherwise `archived_at IS NULL`, which is what `AlbumsScreen` does today and what `AddToAlbumScreen`'s and the picker's "Archived" filter should have done); `smart: false` ⇒ `smart_album_type IS NULL` (AddToAlbum); `search` = name substring. Albums are hundreds: screens read them whole with `useLiveQuery` and no limit. The later "Drag to reorder albums" todo becomes UI only: `repo.update(db, id, { position: keyBetween(…) })`.

Per-cell album stats replace `useAlbumCovers.js`: `features/album-list/useAlbumStats.js` → `useAlbumStats(album)` returns `{ cover, count, lastPostedAt }` from one `useLiveQuery` (`q = assetQuery({ scope: { albumId }, sort: getAlbumSortOrder(album, albumSortOrder) })`: `q.page(db, { limit: 1 })`, `q.count(db)`, and `max(posted_at)` over the album's posts), used by `AlbumListItem` and `PostAlbum`. `AlbumListItem` shows "Posted … ago" on every cell today (its `showLastPostedAt` prop is unused), so the cell keeps showing it; `AlbumLastPostedAt` takes `lastPostedAt` instead of `album`. **[trade]** an asset write re-runs ~20 mounted cells × 3 statements (60–100 ms native). Escalation: one `row_number() over (partition by album_id …)` statement for the visible album ids.

Sort/filter state hooks keep only the key: `useSort` returns `{ sortOrder, sort }` (no comparator maps: `assetSortOptions`, `getAssetSortFunction`, the album and post comparator maps go), `useFilter` returns `{ activeFilter, toggleFilter }` (no `matchFilter`; the per-feature `matchAsset/matchAlbum/matchPost` go). The screens hand the keys to the query builders.

One-off reads live beside the writes, in the repository style (`fn(db, …)`, chunked with `chunk()`): `readByIds(db, table, ids)` (exists) for assets and albums by id (`readAssets`/`readAlbum` are not needed); `assetsRepository.ts` gains `readUnsynced(db, { limit })` and `countUnsynced(db)`, `readWithSyncError(db)`; new `sync/postsRepository.ts` (mirrors `assetsRepository.ts`; `PostsProvider` imports its writes from it) gains `readPostTexts(db)` (all non-empty texts, newest first; `sendAiMessageAsync` draws a random 40 and `AiChatModal` shows the total, unchanged), `readNewestRepostDate(db)` (`max(suggest_repost_at, posted_at)`). Actions on selected ids read with these at action time, not live.

Not used: TanStack Query (no server cache, no stale-while-revalidate; invalidation already exists in the driver), FlashList (v2 runs on SDK 55's New Architecture but changes layout semantics the drag math relies on and web support is unverified — only if FPS measures badly), FTS5, trigger-maintained derived columns (see 1.3), keyset cursors, a shared query cache, an "all-except" selection model, `useLiveTable` for small tables (**[trade]** albums/outbox/sync_log/sync_meta are re-read whole on a write to them, 1–3 ms).

### 1.2 Live updates and re-renders

A refresh produces new row objects, so every mounted cell (~200 in FlatList's default window) re-renders on a write even though `AssetGridCell`/`AssetListItem` are memoized. **[trade]** the cells are cheap and `AssetImage` keys its effects on `thumbnailFilename`/`isThumbnailSynced`. If measured: a 10-line "keep the previous row object when its fields are equal" step inside `usePagedQuery` (reconcile by id), nowhere else.

### 1.3 Derived fields in SQL, not stored

- Asset `lastPostedAt`: `(SELECT max(p.posted_at) FROM post_assets pe JOIN posts p ON p.id = pe.post_id WHERE pe.asset_id = a.id AND pe.deleted_at IS NULL AND p.deleted_at IS NULL)` as a column, only for the `lastPostedAt` sort (the grid shows the value only then; `showLastPostedAt` stays keyed on the sort). Nulls last for `desc` (`ORDER BY last_posted_at IS NULL, last_posted_at DESC`), first for `asc`, matching today's comparators. One correlated form for every scope: its cost scales with the scope (album: its edges; library: 50k index lookups + a temp B-tree, see §2).
- Album `lastPostedAt`: the same aggregate through `album_assets` (`WHERE e.album_id = al.id`), in `albumQuery` for that sort and in `useAlbumStats` for the cell.
- `postHistory`, `album.assets`, `post.assetRefs` disappear as fields; posts of an album/asset are `postQuery` scopes, membership is read where needed, `post.postAssets` carries the edge id + asset.
- Not doing a trigger-maintained `assets.last_posted_at` column: 6 triggers, a backfill, and the driver's table-notification regex would not see trigger writes. Escalation if the sort measures > ~300 ms per read at 50k on a phone (expected 100–200 ms).

### 1.5 Bulk actions

`sync/writeInBatches.ts`: `writeInBatches(ids, write, { onProgress, isCancelled })` runs `write(batch)` per `SQL_BATCH` ids, reports `done / total`, stops between batches when cancelled. The providers' bulk methods (`setAssetsDeleted`, `restoreDeletedAssets`, `deleteAssetsAsync`, `addAssetsToAlbum`, `removeAssetsFromAlbum`) take an optional `{ onProgress, isCancelled }` and loop with it, `requestSync()` once at the end. The screens wire the progress overlay the way `useSaveAssetsToMediaLibrary` does (`show`, `updateProgress`, `hide`); `ProgressOverlayHost` gains a Cancel button when `show({ onCancel })` is given. One pattern, no new context.

## 2. Indexes, pragmas, migrations

`0006_query_indexes.sql` (`npx drizzle-kit generate --name query_indexes`; declare in `db/schema.ts` with `index().on().where(sql)` — drizzle-kit 0.30 emits `WHERE`; `drizzle.config.ts` uses `driver: 'expo'`, which also regenerates `migrations.js`):

```sql
CREATE INDEX assets_live_created_idx ON assets (created_at, id, is_favorite, media_type) WHERE deleted_at IS NULL; -- grid, pager, count, ids
CREATE INDEX assets_deleted_idx      ON assets (deleted_at) WHERE deleted_at IS NOT NULL;                           -- Deleted album
CREATE INDEX assets_unsynced_idx     ON assets (id) WHERE is_synced = 0 AND deleted_at IS NULL;                      -- upload backlog
CREATE INDEX assets_sync_error_idx   ON assets (id) WHERE sync_error IS NOT NULL;
DROP INDEX album_assets_album_idx;
CREATE INDEX album_assets_album_position_idx ON album_assets (album_id, position, asset_id) WHERE deleted_at IS NULL; -- custom order, edgesRepository.liveSorted/add
CREATE INDEX album_assets_asset_idx          ON album_assets (asset_id, album_id) WHERE deleted_at IS NULL;          -- albums of an asset
CREATE INDEX post_assets_asset_idx           ON post_assets (asset_id, post_id) WHERE deleted_at IS NULL;            -- lastPostedAt, posts of an asset
CREATE INDEX posts_live_posted_idx           ON posts (posted_at, id) WHERE deleted_at IS NULL;
```

`post_assets_post_idx` stays. `ORDER BY … DESC, id DESC` walks the same index backwards; drizzle's `"deleted_at" is null` matches the partial predicate.

`0007_drop_row_changes.sql` (last step): remove `rowChanges` from `schema.ts`, `npx drizzle-kit generate --name drop_row_changes`, then prepend the 15 `DROP TRIGGER`s to the generated `DROP TABLE` (like 0004 was edited; the table alone leaves triggers that fail every insert).
