# Plan: per-screen, SQL-backed, paged reads for Squidbox (50k+ assets)

Goal: startup time and memory stay flat as the library grows (target 50,000+ assets, iOS first; the web preview behaves the same). Criteria: SIMPLE, ROBUST, CLEAN, DRY — one data-access pattern everywhere, no caches or derived-state machinery. **[trade]** marks a little performance given up for simplicity.

Verified against the code on 2026-10-14 (after `bfae30f`, albums custom order). Baseline: `npx vitest run` in `apps/mobile` is green (96 tests). Query plans and SQL semantics below were checked on better-sqlite3 (SQLite 3.49).

## Selection and reorder behavior (decided)

Rule from the owner: behavior is intuitive and never silently leaves things out or adds them. Apple's apps and the HIG agree on all three points.

1. **Drag-reorder in albums works under any sort, like Reminders.** A drag under a date sort adopts the order on screen, switches the album to Custom, and the sort menu shows "Custom" at once. There's no confirmation; the date sort is one tap away in the menu. `reorderAlbumAssets(album, { assetId, afterId, sort })` does it in one transaction (`sort` = the order shown, which the provider can't know by itself; `afterId: null` = first): if the album isn't on custom order yet, `edges.reorder(tx, albumId, shown)` writes the shown order once, where `shown` = `assetQuery({ scope: { albumId }, sort }).ids(tx)` followed by the album's remaining live edges (assets that are soft-deleted right now, by position — today's merge in `Album.jsx` appends them the same way, so a restored asset keeps a sane place; `reorder` skips unchanged positions); then `edges.move(tx, albumId, assetId, afterId)` writes one `keyBetween` position between `afterId`'s edge and its next live edge **as the database sees it** (the UI only names the row it dropped after; it never has to know the row below, which may not be loaded), tombstoning duplicate edges of the moved asset; and the album gets `sortOrder: 'custom'`. `move` is sound under these rules, which `liveSorted` sorts by `(position, id)` so every device keeps the same canonical edge; `edgesRepository.test.ts` pins: (a) `afterId`'s edge is that asset's earliest live edge by `(position, id)`; (b) the next edge is the first live edge after it by `(position, id)` — a row-value comparison, one `SEARCH` on `album_assets_album_position_idx` — ignoring the moved asset's own edges; (c) if the two neighbor keys are equal (`keyBetween` throws; two offline devices appending get the same key; a plain `position > ?` would skip a visible row with the same key) `move` falls back to `reorder`; (d) `reorder`'s order is every canonical live edge, including those of soft-deleted assets, and `reorder` tombstones non-canonical duplicates like `move` does, so a duplicate left at its old key can never become the earliest edge and show the asset at its old slot. Every later drag is a one-row write. Smart albums and an active filter or search still disable reorder (`Album.jsx` `reorderEnabled`, unchanged). ([Reminders](https://support.apple.com/guide/reminders/remn922d0b42/mac): "If you drag a reminder in a list that's sorted automatically, the sort option for the list changes to Manual.")
2. **Select all has no cap.** It selects exactly what the current scope, filter and search show, so the header count and "N selected" are always the same number (counts, ids and pages come from the same SQL, with duplicate edges removed in SQL). Bulk actions confirm with the true count ("Delete 50,000 items") and run as chunked, set-based writes behind the progress overlay, with determinate progress and Cancel (HIG, Progress indicators). The writes are already set-based (`saveRecords`: a read, an upsert and an outbox insert per 500 records, one transaction per call); what's left is one transaction per 500 ids, so the queue stays responsive and cancelling between chunks keeps what's already committed (the list is live). See 1.5.
3. **Actions need a selection.** Done: download, add-to-album, post and delete are disabled without one (`SelectionActions.jsx`), and the old "nothing selected → first 500 / all" fallbacks are gone (`a23dbc0`). The Deleted album's explicit "Restore all" / "Delete all" (not in select mode) stay: they say what they do.

## 0. Diagnosis

- The providers (`features/{assets,albums,posts}-context/*Provider.js`) read whole tables through `useLiveCollectionRows/Map` → `useLiveTable` (assets, albums, posts, album_assets, post_assets) and rebuild id-keyed maps with `album.assets`, `post.assetRefs`, `postHistory`, `lastPostedAt` (`sync/derive.ts`, `deriveRecords.ts`, `useDerivedRecords.ts`). Two 50k-row tables (assets, album_assets) are read on every launch; derivations are O(library) in JS; the Albums provider recomputes every album's post history on any post or edge write.
- 40 files call `useAssets/useAlbums/usePosts`; 33 destructure a map and run `Object.values(map)` → `prepareAssets/prepareAlbums/preparePosts` (JS filter/sort/search) → id arrays → `FlatList data={ids}` with map lookups in `renderItem`. `AssetScreen` gets the whole id array in `route.params.assetIds`. `useAlbumCovers` scans every album's assets per write; `CloudSyncProvider` scans all assets per write (`getUnsyncedAssets`, `getAssetsWithSyncError`).
- `row_changes` (migration 0004: 15 triggers, `readLiveRows.ts`, `useLiveTable.ts`) exists only to refresh those maps cheaply and doubles the cost of every insert (todo: "the change-log triggers double the write cost"). Once nothing holds whole tables it has no job.
- Already there and reused, not rebuilt: `sync/useLiveQuery.ts` (`useLiveQuery(read, tables)`: coalesced re-runs on table notifications, keeps data between reads; used by `useRecordCounts`, `useSyncStatus`, `useInspector`, `FirstSyncScreen`), `sync/readByIds.ts` (rows by id incl. tombstones, a statement per 500), `chunk.ts`/`SQL_BATCH`, batched writes (`saveRecords`/`upsertRows`), pulls applied in ~5,000-record transactions (`worker.ts` `APPLY_BATCH`), memoized `AssetGridCell` with stable handlers (`useAssetCells`), one grid setup shared by all asset grids (`useAssetCells`, `useAssetSelectionActions`, `SelectionActions`, `PickerAssetGrid`), `test/performance.test.ts` + `makeMeasuredTestDb` (counts statements, commits, rows read, query-plan lines).

## 1. Target architecture

### 1.1 One hook, one pager, query descriptors

Nothing is held in memory globally. A screen declares what it shows as a small plain object (serializable) and reads it live:

```
sync/watchQuery.ts     watchQuery(db, read, tables, onData) → stop        (the loop, testable in node)
sync/useLiveQuery.ts   useLiveQuery(read, tables, deps = []) → T | undefined  (existing hook, gains `deps`)
sync/usePagedQuery.ts  usePagedQuery(page, tables, deps, pageSize) → { rows, loadMore, hasMore, reset }
```

`watchQuery` is today's `useLiveQuery` effect body moved out: run `read(db)` once, re-run it after a committed write to one of `tables`, never overlap reads (`isLoading/isStale`), stop on `stop()`. It also keeps row identity: when the previous and the new result are arrays of rows with `id`, a row whose fields are shallow-equal to the previous row with that id is the previous object, and when every row is reused and the length is the same the result is the previous array itself, so screens and FlatList don't re-render either (`reuseRows`, ~15 lines in the same file; it applies itself recursively to object or array fields that carry an `id` — an album's `cover`, a post's `postAssets[]` and their `asset` — so those rows reuse too). Memoized cells (`AssetGridCell`, `SortableAssetGridCell`, `AssetItem`) re-render only for rows a write touched, as `deriveRecords` does today. `useLiveQuery` becomes `useState` + one `useEffect` keyed on `tableNames` and `JSON.stringify(deps)` that calls `watchQuery(getDb(), read, …)`; `read` receives the db. A deps change starts a new watch and the old one's late result is dropped by its own stopped flag (no extra generation counter); the previous data stays until the new read lands (no flash to `undefined`). Rule: **`read` must be pure given `deps`** — a notification re-runs the closure captured when deps last changed. Existing callers pass no deps and keep working.

`usePagedQuery` is a growing limit on top of it:

```js
const [limit, setLimit] = useState(pageSize);
const result = useLiveQuery((db) => page(db, { limit: limit + 1 }), tables, [...deps, limit]);
const rows = result?.slice(0, limit);
const hasMore = result ? result.length > limit : false; // limit+1 keeps hasMore true after a delete
const loadMore = () => hasMore && setLimit(nextLimit(limit)); // doubles, step capped at 3,000 rows
const reset = () => setLimit(pageSize);
```

Offset is always 0: first page, load-more and refresh-after-write are the same read, and the database decides the order — no append path, no offset drift, no duplicate keys. The hook never resets the limit by itself; the screen calls `reset()` where it already scrolls to top (`afterSort`, `afterFilter`) and where the search `query` changes (in the change handler, not an effect, so a new search doesn't first re-read at the old depth), so a deep scroll doesn't make every later write (a favorite toggle, a sync pull) re-read that depth for the rest of the session (the Library and Posts tabs never unmount). A reorder doesn't reset: `sessionSortOrder` flips the descriptor synchronously and the loaded grid keeps its depth (1.4). While a load-more read is in flight `hasMore` is false, so repeated `onEndReached` calls are no-ops; VirtualizedList re-checks on content-size change, so a fling chains pages. `nextLimit` doubles the limit until the step reaches 3,000 rows (150, 300, 600, 1,200, 2,400, 4,800, 7,800, 10,800, …): reaching 50k reads ≈ 0.5 M rows in total, not 8 M. **[trade]** memory and the per-write re-read grow with how deep the user scrolled (3,000 rows ≈ 60–120 ms native per re-read, 50k ≈ 1–2 s, 3–5× on web), flat otherwise; the grid holds at most what was scrolled to, never the whole table at startup. Escalation, inside this file only: a sliding window (`offset` near the viewport) once the write-latency gate at limit 10k fails (§4).

Query builders — pure functions of a descriptor, one file per collection, tested on better-sqlite3, exposing only what screens use. Every `ORDER BY` ends with `id` (edges: `e.position, e.id`), so ties (40k never-posted rows, equal edge keys from two offline devices) are stable across refreshes and pages:

- `features/asset-list/assetQuery.js` → `{ descriptor, page, count, ids, tables }`. Descriptor `{ scope, sort, filter, search }`: `scope` = `'library' | { albumId } | 'favorites' | 'deleted'` (the smart albums: `is_favorite = 1` / `deleted_at IS NOT NULL`; every other scope has `deleted_at IS NULL`); `sort` = `createdAt:asc|desc`, `lastPostedAt:asc|desc`, `custom` (album scope only), `random` (`ORDER BY random()`, suggestions only); the Deleted scope has no sort menu and is `deleted_at DESC, id DESC` (today: map insertion order, i.e. arbitrary — this is a stated change: most recently deleted first); `filter` ⊆ `favorites|images|videos` (`media_type`, as `useFilterAssetsAction` does today); `search` = notes substring, see "Search" below. `page(db, { limit })`, `count(db)`, `ids(db)`. `tables` = `[assets]`, + `albumAssets` for an album scope, + `[postAssets, posts]` for a `lastPostedAt` sort. Album membership is one rule in SQL for page, count and ids, so the three agree even with a double edge: date sorts filter `a.id IN (SELECT asset_id FROM album_assets WHERE album_id = ? AND deleted_at IS NULL)`; `custom` drives from the edges and keeps the earliest edge per asset (`NOT EXISTS` an earlier live edge by `(position, id)`, what `derive.ts` `liveOrdered` does). The same `NOT EXISTS` fragment is shared with `postQuery` (`sync/edgeSql.ts`, beside `edgesRepository.ts`).
- `features/post-list/postQuery.js` → `{ descriptor, page, count, tables }`. `scope` = `'all' | { assetId } | { albumId } | { postId } | 'repostCandidates' | 'ignored'`; `sort` = `postedAt:asc|desc` (all), `suggestRepostAt:asc` (candidates: `ORDER BY suggest_repost_at, id`, today's comparator), `updatedAt:desc` (ignored); `filter` ⊆ `favorites`; `search` = text substring (below). Keeps parsing `asset:<id>` / `album:<id>` out of `search` into a scope (as `preparePosts.js` does), so `PostsQueryProvider` and the screens that set that string are untouched. The page read is 3 statements in one `db.transaction` (atomic on the queue): posts → their live `post_assets` (earliest edge per asset, by position) → `readByIds(assets)` (tombstoned assets included, as posts show them today) → each post gets `postAssets: [{ id, asset }]` (what `PostListItem`/`PostAssets`/`PostAssetsEditor` consume). A single post is `postQuery({ scope: { postId } }).page(db, { limit: 1 })` — no second assembly.
- `features/album-list/albumQuery.js` → `{ descriptor, page, tables }`. Albums are hundreds and their sort, filter and search stay in JS for exact parity (`localeCompare` name sort, Unicode-aware search, `sortAlbumsByCustomOrder`, the archived/smart rules of `prepareAlbums`): `albumQuery` only reads. Descriptor `{ scope, assetSort }`: `scope` = `'all' | { assetIds }` (`EXISTS` on `album_assets`, for `PostAlbums`; archived and smart albums included, as today), `assetSort` = the global album-asset sort from `useAppSettings` (the covers depend on it). `page(db)` returns every non-deleted album with its stats as correlated columns in one statement — `assetCount`, `coverAssetId`, `lastPostedAt` — then one `readByIds(assets, coverIds)` attaches `cover`, both in one `db.transaction`. The fast form matters: each stat is a `CASE` on `smart_album_type` (and on `sort_order` for the cover) that chooses between **whole** per-branch subqueries, each with its own plain `WHERE` so its index is used (a shared scope `CASE` inside one subquery's `WHERE` measured 435 ms per album). Branches: `assetCount` = `count(DISTINCT e.asset_id)` over the album's live edges joined to live assets, or `count(*)` of favorites / deleted assets; `coverAssetId` = the first live edge's asset by `(position, id)` when `sort_order = 'custom'`, else the first asset of the album's scope by `assetSort` (the album scope via the membership subquery, the smart scopes via their predicates — the same fragments `assetQuery` uses); `lastPostedAt` = `max(posted_at)` over posts of the album's edges, and `NULL` for smart albums as today (they have no edges; Favorites shows "Never posted" now and keeps doing so — a stated parity choice). Measured on desktop for 300 albums: count ≈ 25 ms, cover ≈ 20 ms (+≈ 40 ms when `assetSort` is `lastPostedAt`), lastPostedAt ≈ 9 ms, so one re-read is ≈ 75–120 ms desktop, ≈ 100–250 ms native, 3–5× on web. `tables` = `[albums, albumAssets, assets, posts, postAssets]`: a write to any re-reads the list once, instead of per cell — and it runs on every asset write while the Albums tab is mounted. If that fails the "Albums mounted" gate in §4, the defined fallback is to pause unfocused screens' live reads: `useLiveQuery(read, tables, deps, { enabled })` stops the watch while `enabled` is false and keeps the last data, re-reading on refocus; the tab screens pass `useIsFocused()`. `useAlbumCovers.js` goes; `AlbumLastPostedAt` reads `album.lastPostedAt` as today. The later "Drag to reorder albums" todo becomes UI only: `repo.update(db, id, { position: keyBetween(…) })`.

**Search** (notes, post text) keeps today's semantics exactly — Unicode-aware, literal, case-insensitive (`toLowerCase().includes`): SQLite's `LIKE`/`lower()` fold ASCII only (`'Über' LIKE '%über%'` is 0) and `LIKE` reads `%`/`_` as wildcards, so the match runs in JS and SQL takes the ids: `page/count/ids` first read `SELECT id, notes FROM assets WHERE notes IS NOT NULL AND deleted_at IS NULL` (posts: `id, text`), filter in JS, and add `AND a.id IN (SELECT value FROM json_each(?))` with the matched ids as one JSON parameter (no 500-variable limit; `json_each` is core SQLite: iOS bundles SQLite 3.50.3, the web's wa-sqlite has it, 30k ids take ≈ 22 ms). Cost: the noted rows' text per read while a search is active (50k noted assets ≈ 60–100 ms native, 3–5× web; the query text is already deferred, `useSearchMode`), plus ≈ 20–60 ms per 30–50k matched ids. Escalation if that measures badly: a JS-lowercased `notes_search` local column written by `upsertRows` (new concept + backfill, not planned).

Sort/filter state hooks keep only the key: `useSort(defaultSortOrder, { afterSort })` returns `{ sortOrder, sort }`; `useSortAlbumsAction` adds `sortFunction` from its comparator map (albums sort in JS), the asset and post comparator maps and `getAssetSortFunction` go; `useFilter` returns `{ activeFilter, toggleFilter }` and `useFilterAlbumsAction` keeps its `matchFilter` (albums), `matchAsset/matchPost` go. Asset and post screens hand the keys to the query builders.

One-off reads live beside the writes, in the repository style (`fn(db, …)`, chunked with `chunk()`): `readByIds(db, table, ids)` (exists) for assets and albums by id; `assetsRepository.ts` gains `readUnsynced(db, { afterId, limit })` (key-walk: `is_synced = 0 AND deleted_at IS NULL AND sync_error IS NULL AND id > ? ORDER BY id LIMIT ?`, so one run tries each asset once whatever `setSyncError` writes), `countUnsynced(db)`, `countSyncErrors(db)`, `readSyncErrors(db, { limit })` (`sync_error IS NOT NULL AND deleted_at IS NULL`, as `getAssetsWithSyncError` today), `countByMediaType(db, ids)` (`json_each`, one statement, for the action-sheet title); new `sync/postsRepository.ts` (mirrors `assetsRepository.ts`; `PostsProvider` imports its writes from it) gains `readPostTexts(db)` (non-empty texts of non-deleted posts, newest first; today's `Object.values(posts)` also includes deleted posts' texts — excluding them is a deliberate change; `sendAiMessageAsync` draws a random 40 and `AiChatModal` shows the total, unchanged) and `readNewestRepostDate(db)` (`max(coalesce(nullif(suggest_repost_at, 0), posted_at, 0))` over non-deleted posts — today's `suggestRepostAt || postedAt || 0`, which `CreatePostScreen` takes over every post including deleted ones; excluding them is a deliberate change, like `readPostTexts`; SQLite's scalar `max(a, b)` is NULL when either is). Actions on selected ids read with these at action time, not live.

Not used: TanStack Query (no server cache, no stale-while-revalidate; invalidation already exists in the driver), FlashList (v2 runs on SDK 55's New Architecture but changes layout semantics the drag math relies on and web support is unverified — only if FPS measures badly), FTS5 (prefix tokens, not substrings), trigger-maintained derived columns (see 1.3), keyset cursors, a shared query cache, an "all-except" selection model, pausing live reads in unfocused tabs from the start (it is the defined fallback for the Albums-mounted gate, 1.1, not the default), `useLiveTable` for small tables (**[trade]** albums/outbox/sync_log/sync_meta are re-read whole on a write to them, 1–3 ms).

### 1.2 Live updates and re-renders

A refresh produces new row objects; `reuseRows` (1.1) hands back the previous object for rows whose fields didn't change, so a favorite toggle re-renders one cell. Posts carry nested `postAssets`, so a post row is new whenever any of its assets changed (few rows per page, fine).

### 1.3 Derived fields in SQL, not stored

- Asset `lastPostedAt`: `(SELECT max(p.posted_at) FROM post_assets pe JOIN posts p ON p.id = pe.post_id WHERE pe.asset_id = a.id AND pe.deleted_at IS NULL AND p.deleted_at IS NULL) AS last_posted_at` in a derived table, only for the `lastPostedAt` sort (the grid shows the value only then; `showLastPostedAt` stays keyed on the sort). The outer `ORDER BY last_posted_at DESC, created_at DESC, id DESC` evaluates it once per row (the `created_at` tie-break keeps the ~40k never-posted assets in date order instead of id order, at the same cost), and SQLite's NULL ordering (first for ASC, last for DESC) is exactly today's comparators, so no `IS NULL` term. One correlated form for every scope: its cost scales with the scope (album: its edges; library: 50k index lookups + a temp B-tree, see §2).
- Album `lastPostedAt`, `assetCount`, `coverAssetId`: correlated columns of `albumQuery.page` (1.1).
- `postHistory`, `album.assets`, `post.assetRefs` disappear as fields; posts of an album/asset are `postQuery` scopes, membership is read where needed, `post.postAssets` carries the edge id + asset.
- Not doing a trigger-maintained `assets.last_posted_at` column: 6 triggers, a backfill, and the driver's table-notification regex would not see trigger writes. Escalation if the sort measures > ~300 ms per read at 50k on a phone (expected 100–200 ms).

## 2. Indexes, pragmas, migrations

`0006_query_indexes.sql` (`npx drizzle-kit generate --name query_indexes`; declare in `db/schema.ts` with `index().on().where(sql)` — drizzle-kit 0.30 emits `WHERE`; `drizzle.config.ts` uses `driver: 'expo'`, which also regenerates `migrations.js`):

```sql
CREATE INDEX assets_live_created_idx ON assets (created_at, id, is_favorite, media_type) WHERE deleted_at IS NULL; -- grid, pager, count, ids
CREATE INDEX assets_deleted_idx      ON assets (deleted_at, id) WHERE deleted_at IS NOT NULL;                       -- Deleted album
CREATE INDEX assets_unsynced_idx     ON assets (id) WHERE is_synced = 0 AND deleted_at IS NULL AND sync_error IS NULL; -- upload backlog walk + count
CREATE INDEX assets_sync_error_idx   ON assets (id) WHERE sync_error IS NOT NULL AND deleted_at IS NULL;            -- error list + count
DROP INDEX album_assets_album_idx;
CREATE INDEX album_assets_album_position_idx ON album_assets (album_id, position, asset_id) WHERE deleted_at IS NULL; -- custom order, membership, edgesRepository.liveSorted/add/move
CREATE INDEX album_assets_asset_idx          ON album_assets (asset_id, album_id) WHERE deleted_at IS NULL;          -- albums of an asset
CREATE INDEX post_assets_asset_idx           ON post_assets (asset_id, post_id) WHERE deleted_at IS NULL;            -- lastPostedAt, posts of an asset
CREATE INDEX posts_live_posted_idx           ON posts (posted_at, id) WHERE deleted_at IS NULL;
```

`post_assets_post_idx` stays. `ORDER BY … DESC, id DESC` walks the same index backwards; drizzle's `"deleted_at" is null` matches the partial predicate.

`0007_drop_row_changes.sql` (last step): remove `rowChanges` from `schema.ts`, `npx drizzle-kit generate --name drop_row_changes`, then prepend the 15 `DROP TRIGGER`s to the generated `DROP TABLE` (like 0004 was edited; the table alone leaves triggers that fail every insert). This halves the first sync's writes again on web, and the account-switch wipe stops logging one change row per deleted row (`accountSwitch.test.ts` must still pass).

`db/client.ts`: `cache_size` is already raised (64 MB cap); nothing else changes here (a journal-mode change is a separate, measured todo, not part of this plan).

Expected plans at 50k (checked on better-sqlite3 with the indexes above): library page and `ids` = `SCAN assets USING INDEX assets_live_created_idx` with no temp B-tree (an ordered index walk prints as SCAN, not SEARCH); `count(*)` = a bare `SCAN assets` or the covering index, ~2–5 ms either way; album custom page = `SEARCH e USING INDEX album_assets_album_position_idx` + PK lookups + the `NOT EXISTS` probe per row + `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` (the `id` tie-break); album date page = the membership subquery + PK lookups + a temp B-tree over the album's assets; `lastPostedAt` = `SCAN a` + a correlated probe per row + temp B-tree; search = `json_each` + PK lookups + temp B-tree; Deleted = `SEARCH assets USING INDEX assets_deleted_idx`, no temp B-tree; posts by `postedAt` = `SCAN posts USING INDEX posts_live_posted_idx`; repost candidates (`suggest_repost_at`) and ignored (`updated_at`) = `SCAN posts` + temp B-tree (no index: posts are few). Costs on an iPhone (statement floor 1–2 ms over JSI; web 3–5×): library page 3–10 ms per 150 rows, count 2–5 ms, `ids` of 50k ≈ 40–70 ms (100–200 ms under `lastPostedAt` or a search: the same ordered read), `limit 3000` ≈ 60–120 ms; album custom page 2–5 ms; `lastPostedAt` sort 100–200 ms per read; albums list with stats 100–250 ms (1.1); search 60–100 ms + 20–60 ms per 30–50k matched ids; `random` is a deliberate full scan once per open (**[trade]**).

The plan guard in `test/performance.test.ts` becomes: for the paged `createdAt`, `custom`, Deleted and posts-by-`postedAt` reads, no line `SCAN <big table>` without `USING (COVERING) INDEX` and no `USE TEMP B-TREE FOR ORDER BY` (a `… FOR LAST TERM OF ORDER BY` on the `id` tie-break is allowed); counts, `lastPostedAt`, album date sorts, search, `random`, repost candidates and ignored posts are listed exemptions with their expected lines.
