# Plan: per-screen, SQL-backed, paged reads for Squidbox (50k+ assets)

Goal: startup time and memory stay flat as the library grows (target 50,000+ assets, iOS first; the web preview behaves the same). Criteria: SIMPLE, ROBUST, CLEAN, DRY — one data-access pattern everywhere, no caches or derived-state machinery. **[trade]** marks a little performance given up for simplicity.

## Selection and reorder behavior (decided)

Rule from the owner: behavior is intuitive and never silently leaves things out or adds them. Apple's apps and the HIG agree on all three points.

1. **Drag-reorder in albums works under any sort, like Reminders.** A drag under a date sort adopts the order on screen, switches the album to Custom, and the sort menu shows "Custom" at once. There's no confirmation; the date sort is one tap away in the menu. `reorderAlbumAssets(album, { assetId, afterId, beforeId })` does it in one transaction: if the album isn't on custom order yet, `edges.reorder(db, albumId, await q.ids(db))` writes the shown order once (it skips unchanged positions); then `edges.move` writes one `keyBetween` position, and the album gets `sortOrder: 'custom'`. Every later drag is a one-row write. Smart albums and an active filter or search still disable reorder. ([Reminders](https://support.apple.com/guide/reminders/remn922d0b42/mac): "If you drag a reminder in a list that's sorted automatically, the sort option for the list changes to Manual.")
2. **Select all has no cap.** It selects exactly what the current scope, filter and search show, so the header count and "N selected" are always the same number. Bulk actions confirm with the true count ("Delete 50,000 items") and run as chunked, set-based writes behind the progress overlay, with determinate progress and Cancel (HIG, Progress indicators). Each chunk of 500 ids is its own transaction: `UPDATE … WHERE id IN (chunk)`, plus one `INSERT INTO outbox … SELECT … ON CONFLICT DO UPDATE` with the clock as `max(updated_at + 1, ?)`. So the queue stays responsive, and cancelling between chunks keeps what's already committed (the list is live). This replaces today's three statements per row in `deleteAssets`, `updateAssets` (restore) and `edges.remove`.
3. **Actions need a selection.** Download, add-to-album, post and delete are already disabled without one (`FloatingHeader.jsx`, `Album.jsx`, HIG: dim unavailable items). The "nothing selected → first 500 / all" fallbacks in `AssetsScreen.jsx` (`handleAddToAlbum`, `getSelectedAssets`) and `Album.jsx` are dead code and get deleted. To act on everything, select all.

## 0. Diagnosis

- The providers (`apps/mobile/src/features/{assets,albums,posts}-context/*Provider.js`) `useLiveTable` whole tables (assets, albums, posts, album_assets, post_assets) and rebuild id-keyed maps with `album.assets`, `post.assetRefs`, `postHistory`, `lastPostedAt` (`sync/derive.ts`, `deriveRecords.ts`). Two 50k-row tables (assets, album_assets) are read on every launch; derivations are O(library) in JS.
- 43 files call `useAssets/useAlbums/usePosts`; 31 destructure a map and run `Object.values(map)` → `prepareAssets/prepareAlbums/preparePosts` (JS filter/sort/search) → id arrays → `FlatList data={ids}` with map lookups. `AssetScreen` gets the whole id array in `route.params`.
- `row_changes` (migration 0004: 15 triggers, `readLiveRows.ts`, `useLiveTable.ts`, `deriveRecords.ts`) exists only to refresh those maps cheaply and costs ~50% on inserts. Once nothing holds whole tables it has no job.

## 1. Target architecture

### 1.1 One hook, one pager, query descriptors

Nothing is held in memory globally. A screen declares what it shows as a small plain object (serializable, so it can travel in `route.params`) and reads it live:

```
sync/useLiveQuery.ts   useLiveQuery(read, tables, deps) → T | undefined
sync/usePagedQuery.ts  usePagedQuery(page, tables, deps, pageSize) → { rows, loadMore, hasMore }
```

`useLiveQuery`: runs `read(db)` on mount and whenever `deps` change; re-runs it after any committed write to one of `tables` (`getDb().onTablesChanged`); keeps the previous data while a read is in flight; drops stale results (generation counter); **coalesces** notifications with the `isLoading/isStale` pattern from today's `useLiveTable.refresh`, so a burst (an incremental pull commits one transaction per page) costs at most two reads per hook. Rule: **`read` must be pure given `deps`** — a notification re-runs the closure captured when deps last changed.

`usePagedQuery` is a growing limit on top of it:

```js
const key = JSON.stringify(deps);
const [state, setState] = useState({ key, limit: pageSize });
if (state.key !== key) setState({ key, limit: pageSize }); // reset during render: no read at the old limit
const result = useLiveQuery(() => page({ limit: state.limit + 1 }), tables, [key, state.limit]);
const rows = result?.slice(0, state.limit);
const hasMore = result ? result.length > state.limit : false; // limit+1 keeps hasMore true after a delete
const loadMore = () => hasMore && setState({ key, limit: state.limit + pageSize });
```

Offset is always 0: first page, load-more and refresh-after-write are the same read, and the database decides the order — no append path, no offset drift, no duplicate keys. While a load-more read is in flight `hasMore` is false, so repeated `onEndReached` calls are no-ops; VirtualizedList re-checks on content-size change, so a fling chains pages. **[trade]** `loadMore` re-reads `0..limit` (3,000 rows ≈ 60–120 ms native, 3–5× on web). Escalation, inside this file only: an append path (`offset: rows.length`, refresh heals).

Query builders — pure, one file per collection, tested on better-sqlite3, exposing only what screens use:

- `features/asset-list/assetQuery.js` → `{ page, count, ids, tables }`. Descriptor `{ scope, sort, filter, search }`: `scope` = `'library' | { albumId } | 'favorites' | 'deleted'` (the smart albums → `is_favorite = 1` / `deleted_at IS NOT NULL`); `sort` = `createdAt:asc|desc`, `lastPostedAt:asc|desc`, `custom` (album scope only, `ORDER BY e.position`), `random` (`ORDER BY random()`, for suggestions); `filter` ⊆ `favorites|images|videos`; `search` = notes substring. `tables` = `[assets]` + `albumAssets` for an album scope + `[postAssets, posts]` for a `lastPostedAt` sort. Double edges (`edges.add` already prevents them) are deduped by one JS line over the page.
- `features/post-list/postQuery.js` → `{ page, count, tables }`. `scope` = `'all' | { assetId } | { albumId } | { postId } | 'repostCandidates' | 'ignored'`; keeps parsing `asset:<id>` / `album:<id>` out of `search` (as `preparePosts.js` does) so `PostsQueryProvider` and the screens setting that string are untouched. The page read is 3 statements: posts → `post_assets` for those posts → `assets` for those edges → each post gets `postAssets: [{ id, asset }]` (what `PostListItem`/`PostAssets` consume today). A single post is `postQuery({ scope: { postId } }).page(db, { limit: 1 })` — no second assembly.
- `features/album-list/albumQuery.js` → `{ page, tables }`. `scope` = `'all' | { assetIds }` (`EXISTS` on `album_assets`), `sort`, `filter`, `search`. Albums are hundreds: screens read them whole with `useLiveQuery` and no limit.

One-off reads live beside the writes, in the existing repository style (`fn(db, …)`, chunked with `chunk()`): `assetsRepository.ts` — `readAssets(db, ids)`, `readUnsynced(db, { limit })`, `readWithSyncError(db)`; new `sync/postsRepository.ts` (mirrors `assetsRepository.ts`) — `readPostTexts(db)` (all non-empty texts; `sendAiMessageAsync` draws a random 40 and `AiChatModal` shows the total, unchanged), `readNewestRepostDate(db)`; `readAlbum(db, id)` beside `makeRepository`'s album use. Actions on selected ids read with these at action time, not live.

Not used: TanStack Query (no server cache, no stale-while-revalidate; invalidation already exists in the driver), FlashList (v2 runs on SDK 55's New Architecture but changes layout semantics the drag math relies on and web support is unverified — only if FPS measures badly), FTS5, trigger-maintained derived columns (see 1.3), keyset cursors, a shared query cache, an "all-except" selection model, `useLiveTable` for small tables (**[trade]** albums/outbox/sync_log/sync_meta are re-read whole on a write to them, 1–3 ms; `useSyncStatus.ts` and `useInspector.ts` switch to `useLiveQuery`).

### 1.2 Live updates and re-renders

A refresh produces new row objects, so every mounted cell (~200 in FlatList's default window) re-renders on a write. **[trade]** `AssetListItem` is cheap and `AssetImage` keys its effects on `thumbnailFilename`. If measured: a 10-line "keep the previous object when shallow-equal" step inside `useLiveQuery`.

### 1.3 Derived fields in SQL, not stored

- Asset `lastPostedAt`: `LEFT JOIN (SELECT pe.asset_id, max(p.posted_at) AS last_posted_at FROM post_assets pe JOIN posts p ON p.id = pe.post_id WHERE pe.deleted_at IS NULL AND p.deleted_at IS NULL GROUP BY pe.asset_id) lp ON lp.asset_id = a.id`, only for the `lastPostedAt` sort (the grid shows the value only then). Nulls last for `desc` (`ORDER BY lp.last_posted_at IS NULL, lp.last_posted_at DESC`), first for `asc`, matching today's comparators.
- Album `lastPostedAt`: the same aggregate joined through `album_assets`, grouped by album; only for that sort.
- `postHistory`, `album.assets`, `post.assetRefs` disappear as fields; posts of an album/asset are `postQuery` scopes, membership is read where needed.
- Not doing a trigger-maintained `assets.last_posted_at` column: 6 triggers, a backfill, and the driver's table-notification regex would not see trigger writes. Escalation if the sort measures > ~300 ms per read at 50k on a phone (expected 100–200 ms).

## 2. Indexes, pragmas, migrations

`0005_query_indexes.sql` — declare in `db/schema.ts` with drizzle's `index().on().where(sql)` (drizzle-kit 0.30 emits `WHERE`; `drizzle.config.ts` already uses `driver: 'expo'`):

```sql
CREATE INDEX assets_live_created_idx ON assets (created_at, id, is_favorite, media_type) WHERE deleted_at IS NULL; -- grid, pager, count, ids
CREATE INDEX assets_deleted_idx      ON assets (deleted_at) WHERE deleted_at IS NOT NULL;                           -- Deleted album
CREATE INDEX assets_unsynced_idx     ON assets (id) WHERE is_synced = 0 AND deleted_at IS NULL;                      -- upload backlog
CREATE INDEX assets_sync_error_idx   ON assets (id) WHERE sync_error IS NOT NULL;
DROP INDEX album_assets_album_idx;
CREATE INDEX album_assets_album_position_idx ON album_assets (album_id, position, asset_id) WHERE deleted_at IS NULL; -- custom order, edgesRepository.liveSorted
CREATE INDEX album_assets_asset_idx          ON album_assets (asset_id, album_id) WHERE deleted_at IS NULL;          -- albums of an asset
CREATE INDEX post_assets_asset_idx           ON post_assets (asset_id, post_id) WHERE deleted_at IS NULL;            -- lastPostedAt, posts of an asset
CREATE INDEX posts_live_posted_idx           ON posts (posted_at, id) WHERE deleted_at IS NULL;
```

`post_assets_post_idx` stays. `ORDER BY … DESC, id DESC` walks the same index backwards; drizzle's `"deleted_at" is null` matches the partial predicate.

`0006_drop_row_changes.sql` (last step, hand-written like 0004): the 15 `DROP TRIGGER`s **first**, then the `DROP TABLE row_changes` drizzle-kit generates once `rowChanges` leaves `schema.ts` (the table alone leaves triggers that fail every insert). On web this halves the first sync's writes again (measured: 28 s → 14 s of apply at 50k) and turns the 138 s wipe on account switch into ~2 s.

`db/client.ts`: `cache_size` is already raised (64 MB cap). Add `PRAGMA journal_mode = WAL` on iOS only (expo-sqlite sets no journal mode); on web's OPFS VFS, WAL needs exclusive locking and measured slower.

Expected plans/costs at 50k on an iPhone (statement floor 1–2 ms over JSI; web 3–5×), asserted with `EXPLAIN QUERY PLAN` in vitest on better-sqlite3: library page `SEARCH assets USING INDEX assets_live_created_idx`, no temp B-tree, 3–10 ms per 150 rows, count 2–5 ms, `ids` of 5k ≈ 20 ms, `limit 3000` ≈ 60–120 ms; album custom page `SEARCH album_assets USING INDEX …position_idx` + PK lookups, 2–5 ms; `lastPostedAt` sort (assets or the albums list) materialized aggregate + temp B-tree, 100–200 ms per read; notes `LIKE '%q%'` 30–60 ms (debounce 150 ms).

## 4. Risks and measurements

Risks: a partial index silently unused if a predicate drifts (plan tests); `lastPostedAt` cost is an estimate (escalation defined); `maintainVisibleContentPosition` with horizontal `pagingEnabled` — verify on device in step 4; during steps 3–4 the pager's SQL order can differ from a not-yet-converted JS order (none after step 3 for asset grids); a paged custom album only allows drops between loaded cells (fine).

Measure before step 3, after 3, after 7 (`npm run seed:mock -- --assets 50000` in `apps/server`): startup → first grid paint (web `--production` + `performance.mark`s via Playwright; native `console.time`, Perf Monitor RAM); per-statement cost (`__dbStats`, or a `__DEV__` version kept in `driver.ts`); scroll FPS on a long fling (Perf Monitor; web `PerformanceObserver('longtask')`); memory at idle, after scrolling to limit 3,000 and 50,000, after 20 pager open/close cycles; write latency from `toggleFavoriteAsset` to the next rows at limit 150/3,000/50,000, with and without the Albums tab mounted; `lastPostedAt` sort on the asset grid and the albums list; a manual checklist (drag-select across pages, select-all + delete + cancel at 50k, reorder in a 1,000-asset custom album, pager deletion of the current asset, post scopes).
