# What the field says about keeping a codebase healthy (evidence notes)

Researched 2026-11-08 for an agent-run periodic architecture review of an agent-maintained TypeScript codebase. Each claim carries a source; **[measured]** = empirical data, **[vendor]** = vendor-run data, **[opinion]** = practitioner argument. Where I could not reach a primary source I say so.

## 1. What is a "healthy codebase", and how is it measured?

**CodeScene Code Health / Tornhill.** Code Health is a proprietary 1–10 file score aggregating ~25 factors (brain methods, nesting, duplication, etc.). _Code Red_ (Tornhill & Borg, TechDebt 2022, 39 proprietary codebases, 30,737 files) reports low-health code has ~15× more defects and issues take ~124% longer on average to resolve, with up to 9× cycle-time variance; the metric was validated only by correlating with issue-resolution time (r = −0.58). **[vendor-run, observational, authors are the vendor]** — https://arxiv.org/abs/2203.04374. A follow-up, _Ghost Echoes Revealed_ (Borg, Udayakumar, Tornhill 2024), benchmarks Code Health against SonarQube's Maintainability Rating and the Maintainability Index using human assessments; claims Code Health matches ML and SonarQube has a high false-positive rate **[vendor]** — https://arxiv.org/abs/2408.10754. CodeScene's own docs: hotspots = high change frequency × low Code Health; change coupling is a _signal_, not always bad (tests legitimately co-change) — https://docs.enterprise.codescene.io/versions/6.3.3/guides/technical/hotspots.html. Enforcement: trend plus a gate on _new/changed_ code.

**SonarQube "Clean as You Code".** Quality gates apply only to a "new code" period (previous version, N days, reference branch); overall-code conditions are explicitly discouraged **[vendor practice, no outcome evidence published]** — https://docs.sonarsource.com/sonarqube-server/latest/project-administration/setting-up-clean-as-you-code. The idea is the ratchet: never let the delta get worse.

**Google.** The reviewer standard is "approve once the CL definitely improves the overall code health of the system, even if it isn't perfect"; code health is described (maintainability, readability, understandability) but never quantified — https://google.github.io/eng-practices/review/reviewer/standard.html. Small CLs are preferred because they are reviewed faster and more thoroughly **[opinion/internal practice]** — https://google.github.io/eng-practices/review/developer/small-cls.html. Enforcement: human review, not metrics.

**SPACE / DORA.** SPACE (Forsgren, Storey et al., ACM Queue 2021) is about developer productivity; code health is not a dimension. DORA 2025 (Google Cloud): ~90% AI adoption; AI now associated with higher throughput but also higher delivery _instability_ (change-fail rate, rework rate); "AI is a mirror and multiplier" **[measured survey, correlational]** — https://dora.dev/research/2025/dora-report/ (summary of figures via https://rdel.substack.com/p/rdel-112-whats-ais-impact-on-software; the report page itself does not state them). Neither framework measures code health directly; they measure its downstream symptoms.

**Technical-debt research.** Ernst, Kazman & Delange, _Technical Debt in Practice_ (MIT Press 2021) widen debt to requirements, architecture, test, documentation and deployment debt **[synthesis]** — https://mitpress.mit.edu/9780262542111/technical-debt-in-practice/. The actionable thread across this literature: locate debt by behaviour (change frequency, co-change), not by static complexity alone.

**Maintainability Index.** The 1994 regression formula was reused by tools without recalibration; it averages power-law metrics per file, so it hides the few high-risk files; SIG found LOC to be as informative **[measured critique]** — van Deursen 2014, https://avandeursen.com/2014/08/29/think-twice-before-using-the-maintainability-index/, citing Heitlager, Kuipers & Visser 2007, https://www.di.uminho.pt/~joost/publications/HeitlagerKuipersVisser-Quatic2007.pdf. Lesson: never report a single codebase-wide average; report the tail.

**Fitness functions.** Ford, Parsons & Kua define an architectural fitness function as "an objective integrity assessment of some architectural characteristic(s)", run triggered (CI) or continually **[opinion/framework; no outcome studies found]** — https://www.infoq.com/articles/fitness-functions-architecture/.

**Summary of evidence strength.** The only outcome-linked code-health metric with a large sample is CodeScene's, and it is vendor-run. Everything else is practitioner consensus. The convergent, defensible practices are: measure the _tail_ (worst files), weight by _change frequency_, gate the _delta_, and track _trend_.

## 2. How is health enforced mechanically?

- **Dependency boundaries.** Nx `enforce-module-boundaries` (tag-based constraints on project imports, checks TS imports and package.json) — https://nx.dev/docs/features/enforce-module-boundaries. dependency-cruiser runs rules on the resolved module graph; Ghost moved there from a custom ESLint rule because the ESLint rule only saw `require()` (changelog surfaced in search; **[practitioner report]**).
- **Ratchets / baselines.** ESLint bulk suppressions (April 2025) record existing violations per rule/file in a committed file; `--prune-suppressions` tightens it — https://eslint.org/blog/2025/04/introducing-bulk-suppressions/. Betterer-style tests fail on new issues and lock in fixes; a "budget" caps counts **[tool docs]**. Rot reported: baselines nobody owns become permanent exemptions **[opinion]**.
- **Mutation testing.** Google mutates only changed lines during review and surfaces mutants as review comments; developers exposed to it longer write more and better tests **[measured, in-house]** — Petrović et al., TSE 2022, https://arxiv.org/abs/2102.11378. Stryker (JS/TS): `incremental` mode and `thresholds.break` as a CI gate — https://stryker-mutator.io/docs/. Mutation score is the standard check that generated tests actually constrain behaviour (see §3).
- **Property-based / model-based tests for CRDT & sync.** MET (Model-checking-driven testing of CRDTs) shows convergence properties over ≤3 concurrent operations suffice for eventual convergence, so small generated scenarios are enough **[measured]** — https://arxiv.org/abs/2204.14129. Jepsen on TigerBeetle: "DST is essentially property-based testing with techniques to turn non-deterministic systems into deterministic ones" — https://jepsen.io/analyses/tigerbeetle-0.16.11.pdf. No primary Automerge/Yjs fuzz-harness write-up surfaced.
- **Deterministic simulation and fault injection.** TigerBeetle VOPR: deterministic from seed + commit, time-compressed, fault levels controllable — https://docs.tigerbeetle.com/about/vopr. Antithesis: hypervisor-level determinism, injects clock/network/scheduling faults — https://antithesis.com/docs/resources/deterministic_simulation_testing/. Graft (offline-first storage engine) reports Antithesis found a crash-during-commit + timeout-during-recovery bug that reset replication pointers **[practitioner report]** — https://sqlsync.dev/posts/antithesis-driven-testing. Crash-consistency injection for SQLite-backed local-first apps: no dedicated source found; the Graft case is the closest.
- **What rots.** Flaky tests cost ~1.3% of developer time in one industrial study **[measured]** — ICST 2024, https://conf.researchr.org/details/icst-2024/icst-2024-industry/1/Cost-of-Flaky-Tests-in-CI-An-Industrial-Case-Study. Visual baselines and ratchet baselines rot the same way: when nobody owns them they are either mass-approved or deleted (§5).

## 3. Vibe coding and agent-maintained code (2025–2026)

- **Karpathy** coined "vibe coding" on 2 Feb 2025 for throwaway weekend projects ("forget that the code even exists"); the pushback was about applying it to production. Willison proposed "vibe engineering" (7 Oct 2025) for accountable professional use, with "agentic engineering" winning by Feb 2026 **[opinion]** — https://simonwillison.net/2025/Oct/7/vibe-engineering/.
- **GitClear** (211M changed lines, 2020–2024): cloned code 8.3% → 12.3% of changed lines; moved (refactored) code 25% → <10%; churn up **[vendor, correlational, AI attribution method not disclosed]** — https://www.gitclear.com/ai_assistant_code_quality_2025_research.
- **METR RCT** (16 experienced OSS devs, 246 issues, Cursor + Claude 3.5/3.7, July 2025): 19% _slower_ with AI; developers forecast +24% and still believed +20% afterward. Authors: small n, early-2025 tools, familiar million-line repos **[measured]** — https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/. Key lesson for an owner who reads no code: self-report of speed is unreliable.
- **Tests that agree with bugs.** Konstantinou, Degiovanni & Papadakis 2024: LLM oracles tend to capture _actual_ rather than _expected_ behaviour — https://arxiv.org/abs/2410.21136. Mathews & Nagappan 2024: CoverAgent/CoverUp can validate buggy code — https://arxiv.org/abs/2412.14137. Konstantinou, Tambon & Papadakis 2026: tests generated after seeing faulty code catch 14% of faults vs 25% when generated independently **[measured]** — https://arxiv.org/abs/2607.05139. Mitigations with evidence: generate tests from spec with implementation withheld; multi-agent oracle consensus (CANDOR, +25pp oracle correctness, https://arxiv.org/abs/2506.02943); mutation score as the check.
- **"Agents copy the nearest pattern."** Widely repeated (agents retrieve by similarity, not quality; a deprecated comment does not lower rank; each generated instance becomes retrieval context for the next) **[opinion; quantitative support is one 840-line vendor benchmark]** — https://gabeorlanski.github.io/posts/agent-copy-pasta, https://agentpatterns.ai/anti-patterns/pattern-replication-risk/. Proposed fix with partial evidence: encode anti-patterns as lint rules, because "prose loses to codebase examples".
- **CLAUDE.md / AGENTS.md as routing tables.** Anthropic: context fills fast, performance degrades; keep CLAUDE.md to what cannot be inferred — https://code.claude.com/docs/en/best-practices. Vercel eval (27 Jan 2026, Next.js 16 APIs outside training data): baseline 53%, skills 53%, skills with explicit instructions 79%, an ~8 KB compressed AGENTS.md _index of docs_ 100% **[measured, single vendor eval]** — https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals.
- **Reviewing without reading.** Spec-driven development (GitHub Spec Kit, Kiro) puts a spec, not a chat, at the centre; Fowler's site compares the tools **[opinion]** — https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html. StrongDM's "scenarios outside the codebase as a holdout set" is the clearest statement of acceptance tests as the contract the agent cannot rewrite (§4). No study measures outcomes of review-free workflows.

**Recurring failure modes:** duplication over reuse; tests that mirror the implementation; drift toward whatever pattern is nearest; over-confident self-reports. **Mitigations with some evidence:** spec-first tests, mutation score, lint-encoded conventions, compact index-style agent docs.

## 4. The "dark factory" for software

- **Term origin (software).** Dan Shapiro, "The Five Levels: from Spicy Autocomplete to the Software Factory" (Jan 2026): level 5 = a black box turning specs into software, named after lights-out manufacturing — https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/ (via https://simonwillison.net/2026/Jan/28/the-five-levels/). **Factory.ai does not use "dark factory"**; it calls itself an "agent-native software factory … under human direction" — https://factory.ai/news/series-c. The term is applied to it only by third parties.
- **StrongDM Software Factory** (Justin McCarthy, 6 Feb 2026; three-person team since July 2025). Charter: "Code must not be written by humans. Code must not be reviewed by humans." Claimed needs: (a) _scenarios_ — end-to-end user stories kept outside the codebase like an ML holdout set, judged flexibly by an LLM so agents cannot rewrite them; (b) _satisfaction_ — a probabilistic score (fraction of trajectories that likely satisfy the user) replacing pass/fail; (c) _Digital Twin Universe_ — behavioural clones of Okta, Jira, Slack, Google Docs/Drive/Sheets allowing thousands of scenarios/hour; (d) an economic heuristic: ≥ $1,000/day in tokens per engineer **[practitioner report, no independent audit]** — https://factory.strongdm.ai/.
- **Critiques.** Stanford CodeX (Kahana, 8 Feb 2026): builder and inspector share blind spots; Goodhart on satisfaction scores; accountability gaps; skill atrophy; needs disclosure standards and warranties tied to scenario coverage and replica fidelity **[opinion/legal]** — https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/. Others: scenarios are only as good as their author; unproven beyond a 3-person team; integration-heavy domains suit it, others unclear; "a rising revert rate is the signal to turn the light back on" — https://dev.to/soaresdiogo/dark-factory-vs-light-factory-where-should-ai-agents-run-unwatched-9po. OpenHands: it is "not software development without engineers"; humans set goals and constraints **[vendor opinion]** — https://www.openhands.dev/blog/what-is-an-ai-dark-factory.
- **Adjacent framings.** "The autonomous codebase" (LeadDev, Sept 2026): greenfield is solved, brownfield maintenance is not; needs codebase-wide context — https://leaddev.com/software-quality/the-autonomous-codebase. IBM "AI Codebase Maturity Model" (arXiv Apr 2026) defines maturity by _feedback-loop topology_, not autonomy; one 4-month case study — https://arxiv.org/abs/2604.09388. RACER (FSE 2026 industry): autonomous refactoring agents must also _choose_ what to fix — https://conf.researchr.org/details/fse-2026/fse-2026-industry-papers/10/. "Self-maintaining codebase" and "AI-native codebase" appear mainly in vendor marketing with no evidence.

**Bluntly:** one publicised team, no independent audit, no outcome data. What all proponents agree it needs is the same list: external specs/scenarios the agent cannot edit, simulated dependencies, telemetry, and an economic/revert signal that tells humans when to look.

## 5. UI/UX and design-system health

- **Defining and measuring adoption.** Common metrics: component reuse rate (share of UI built from system components), adoption rate (projects using the library), design-to-code parity, deprecated-component count, and falling custom-CSS growth **[practitioner]** — https://www.cbinsights.com/research/team-blog/design-system-success, https://designsystem.morningstar.com/whats-new/blog/tracking-system-adoption-and-usage (Morningstar: usage ≠ coverage ≠ quality; they combine codebase scans, surveys and coverage assessments). zeroheight 2025/2026 reports (~300 respondents): only 38% of systems reach wide adoption; teams track component usage and accessibility compliance, almost none ROI **[measured survey, vendor]** — https://othr.zeroheight.com/hubfs/zeroheight%20-%20Design%20System%20Report%202025%20-%20release%20version.pdf. No standard composite "design-system health score" exists;
- **Token lint rules.** Mozilla's stylelint `use-design-tokens` forbids hard-coded colours, enabled per property for gradual rollout — https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens.html. Atlassian's ESLint `ensure-design-token-usage` lints colour/spacing/shape domains — https://atlassian.design/components/eslint-plugin-design-system/ensure-design-token-usage. For React Native `StyleSheet`/Tailwind arbitrary values no published rule surfaced; teams write custom rules **[gap]**. Figma itself names "hardcoded design tokens that drift over time" as the usual failure — https://www.figma.com/blog/design-systems-ai-mcp/.
- **Visual regression and its rot.** Playwright `toHaveScreenshot`, Chromatic and Percy work, but one team reports ~380 baselines nobody trusted, deleted after six months; consensus: baseline only high-risk flows, use DOM assertions elsewhere **[anecdote]**; mass-approving a batch makes the regression the new baseline **[opinion]**. Flake cost evidence as in §2.
- **Storybook as contract.** Stories plus interaction tests and the a11y addon run per story in CI; `parameters.a11y.test = 'error'` fails CI **[tool docs]** — https://storybook.js.org/docs/writing-tests/accessibility-testing. A component gallery (this repo already has one under Settings → Components) is the same idea.
- **Accessibility.** Deque's axe-core study: automation fully covers ~57% of issues by volume (80% with guided testing) **[vendor, 2021, no replication]** — https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues. Automated checks miss meaningful alt text, focus order and complex interactions.
- **UX writing.** Vale turns a style guide (terminology, branding, banned words) into YAML rules run in CI with error/suggestion severities; used by Datadog, GitLab, Spectro Cloud for docs **[practitioner]** — https://www.datadoghq.com/blog/engineering/how-we-use-vale-to-improve-our-documentation-editing-process, https://www.spectrocloud.com/blog/how-we-use-vale-to-enforce-better-writing-in-docs-and-beyond. Nobody surfaced runs it over UI strings; it needs string extraction first **[gap]**.
- **Agents drifting from the design system.** Named problem: agents "hallucinate component behaviour from incomplete prompts" and emit hard-coded values; mitigations are Figma MCP + Code Connect (component→code mapping) and a generated rules file **[vendor opinion, no benchmarks]** — https://www.figma.com/blog/design-systems-ai-mcp/, https://developers.figma.com/docs/code-connect/.

**Evidence here is thin:** mostly tool docs, vendor surveys and anecdotes. The convergent practice is the same as §1–2: lint the convention (tokens, components, labels), measure the tail (one-off styles, raw primitives), and keep the gallery as the executable contract.

## Implications for a periodic agent-run architecture review

1. **Report the tail, never an average.** List the worst N files by (change frequency × health) and the trend of that list; MI-style averages hide the risk (van Deursen 2014; CodeScene hotspots).
2. **Gate the delta, trend the whole.** Fail on new violations in changed code (SonarQube Clean as You Code; ESLint bulk suppressions) and record a per-review baseline so the owner's summary shows "better / same / worse" counts, not absolutes.
3. **Encode every convention as a rule, not prose.** Agents copy the nearest example and lose prose to code (Orlanski; agentpatterns); each review should turn one recurring finding into a lint/dependency-cruiser/Betterer rule and remove the paragraph from CLAUDE.md.
4. **Keep CLAUDE.md an index.** Vercel's eval favours a compact pointer index over long instructions; the review should shrink CLAUDE.md and move detail to referenced files or skills.
5. **Measure test strength, not coverage.** Run Stryker incrementally on changed sync/repository code and report mutation score; LLM tests tend to mirror the implementation (Konstantinou et al. 2024/2026; Petrović et al. 2022).
6. **Keep acceptance scenarios the agent cannot edit.** Spec-first tests outside the normal edit path, in the owner's words (StrongDM scenarios; SDD). The review checks they still exist, still run, and still fail when a mutation breaks them.
7. **For the sync engine, add seeded model-based tests** over ≤3 replicas with shuffled delivery and crash-in-commit faults (MET; Graft/Antithesis; TigerBeetle VOPR) and treat a failing seed as a pinned regression test.
8. **Watch the outcome signals, not self-reports.** Track revert/rework rate and change-fail rate per period (DORA 2025; the "turn the light back on" critique); METR shows agents' and humans' speed self-reports are unreliable.
9. **UI: lint tokens and primitives.** A rule set for hard-coded colours/spacing, raw `TextInput`/menu primitives and spread styles in features (Mozilla, Atlassian token rules; this repo's CLAUDE.md UI section); report count and trend of one-off styles per feature.
10. **UI: treat the component gallery as the contract.** Every exported component in `src/components` has a gallery entry with interaction and a11y checks running in CI (Storybook pattern, axe at `error`); the review lists components without one.
11. **UI: audit copy, not just code.** Extract UI strings and run a Vale-style terminology check against the app's one-name-per-feature rule (Datadog/GitLab Vale practice); report new synonyms introduced since last review.
12. **UI: screenshot only what a user would complain about.** A small, owned set of visual baselines for key screens, reviewed each cycle; never mass-approve (visual-regression rot reports). Explain each diff in the owner's summary in one sentence.
13. **Avoid metric theatre.** Don't invent a composite health score; Goodhart applies to satisfaction scores (Kahana 2026) and to Code Health alike. Report a handful of named, trended signals and the concrete fixes proposed.
